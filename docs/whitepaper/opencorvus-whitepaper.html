Technical Whitepaper · v2026.05

OpenCorvus

A multi-agent harness for reliable code delivery.
围绕编码 Agent 的多角色编排框架——把用户请求经过 spec / contract / build / audit / delivery 多阶段流水线， 产出与机器可校验契约一致的交付物。

作者OpenCorvus Contributors发布2026-05-14许可MIT

01问题陈述

当前 AI 编码工具普遍采用单 Agent + 单循环结构：模型读取上下文 → 写代码 → 用户审查 → 纠正。 这种结构在 1–2 文件的局部修改上表现良好，但在需要多阶段规划、跨模块协作、端到端可验收的任务上失败率显著上升。 主要原因可观察为四类：

  • 需求漏覆盖——模型在长上下文中遗忘早期约束；
  • 覆盖度不均——擅长部分写得过细，不擅长部分一笔带过；
  • 失败不可局部回退——单循环出错后只能整体重写；
  • 无审计踪迹——决策路径不可追溯，无法定位“在哪一步、基于什么事实做出了什么选择”。

OpenCorvus 的设计前提是：当前 LLM 的能力已经足够，受限的是工程纪律—— spec 化、契约化、可审计化、可独立验收化。这套纪律若交由模型在 prompt 层自行管理，几乎一定被省略； 本项目将其下沉到框架层，通过多 Agent 流水线、机器可校验契约、append-only 审计踪迹、自动 replan 闭环来强制兑现。

因此每个任务先经过 意图分析 → 需求 → 架构 三道前置关，把请求转译为可枚举的 REQ 列表 （REQ-1、REQ-2 … 序号化）与机器可校验的接口契约（Contract IR + Graph）， 再交由实现层调度外部编码执行器；交付前由独立审计与交付角色复核，不通过则自动重计划。 本白皮书余下章节按此顺序展开。

血缘：在 opencode 之上做了什么

OpenCorvus 仓库 fork 自 sst/opencode （早期是 Kujtim Hoxha 起步的 termai → opencode-ai/opencode 演进而来）。 fork 之后的工作不是“改造 opencode”，而是在它之上引入一整套新的编排抽象。 下面是 fork 前不存在、由 OpenCorvus 从零设计的独创子系统：

子系统核心贡献
architect/ 从零设计的 Contract IR + ArchitectContractGraph——把模糊需求转译为 Zod schema 化的接口契约 DAG，含 5 种 ValueDomain、循环 / 孤立消费者等多种静态校验
integrity/ 四维完整性审计框架——Requirement Fidelity / Technical Feasibility / Hallucination / Solution Quality，通过 prompt 注入正交审查维度
acceptance/ 四族评分器抽象——Heuristic / LLM Judge / Prebuilt / Contract Audit；其中 Contract Audit 是零 LLM 的 AST 静态校验路径
delivery/ + prosecutor/ 评审 + 对抗双角色——Delivery 无修复权的 verdict 关卡，Prosecutor 专门寻找未被指标覆盖的失败模式
scheduler/ + protocol/ 事件驱动唤醒循环——TaskQueueService 串行调度 + protocol_event append-only seq 单调递增，让进程崩溃也能从事件序列恢复
../channel-runtime/ 15 个消息通道适配器——把同一个 headless 编排器同时暴露给 Slack / 飞书 / 钉钉 / QQ / HTTP Webhook 等渠道
decision-log/ 跨 Agent 共享的决策审计层——记录“为什么”而非“做了什么”

OpenCorvus 内置的默认执行器命名为 mirrorcode，致敬这段血缘。 定位关系一句话总结：

  • opencode / Claude Code / Codex CLI / aider / cline是单点编码工具——一个模型 + 一个工具循环 + 一个用户。
  • OpenCorvus 是编排框架——它把上述工具当作 executor 之一调用， 在它们之上套一层 9 角色团队、契约图、append-only 审计、重计划循环。

03Harness 的角色边界

“Harness”在本项目中指套在 LLM 外侧的工程约束层——它不参与生成本身， 只负责把生成结果与可验证的工程规约（spec、契约、审计踪迹、验收评分）绑定。 下表给出两种结构在工程场景下可观察的差异：

单 Agent 模式

  • 需要盯人：每一步等用户审查、纠偏。
  • 覆盖不均：易做的写得多，难做的一笔带过。
  • 失败成本高：整体重写，无法局部回滚。
  • 无审计：错在哪个决策？回不到现场。

Agent 团队模式（OpenCorvus）

  • 无人值守：编排器自驱 spec → goal → build → eval 循环。
  • 覆盖强制：Integrity 四维审计逐条对照 REQ-N 才放行。
  • 失败可重计划：自动 replan 受影响的 goal 而非全推倒。
  • 全程留痕：决策日志 + Append-only 工件 + 契约图。

04编排总览：事件驱动的单任务架构

OpenCorvus 的运行时由三个职责正交的层构成：HTTP / SSE 网关与序列化调度；Orchestrator LLM 主控会话； append-only 工件与事件序列。前者把外部请求转译为可调度的唤醒事件，中者基于事件做出下一步决策并调用专业 Agent， 后者承载所有过程事实供后续唤醒读取。

入口

Engine Service

HTTP / SSE 网关、任务路由、序列化调度。接收用户请求、生成 task_id、根据事件触发“唤醒”。

大脑

Orchestrator LLM

编排器本身是一个 LLM 会话，持有任务整体上下文，通过调用工具调度其他 Agent，决定下一步该做什么。

记忆

Append-only Artifacts

所有过程事实（goal、attempt、verdict、patch）按约定只追加不修改地写入 engine_artifact 与 protocol_event。

唤醒循环：流程不由代码硬编码

外部事件（用户消息、Agent 完成、Eval 结果回流）触发 Engine 对该任务发起一次 wake。 Orchestrator LLM 读取该任务全部 append-only 事实，自行决定下一步调度的工具。 这意味着流程控制不存在于任何 if / else 或状态枚举中——它是 LLM 在事实集合上的实时决策投影。 这一设计的代价是：编排路径不可静态可视化、debug 依赖事件回放；收益是：模型决策与流程逻辑同源、任何状态都可由事件重建。

五条设计红线

项目层面贯穿的硬约束，文档中所有设计决策须与之相容：

  • 禁止双源——每个功能只有一种实现，删旧不留兼容；
  • 禁止 fallback——失败抛错而非静默降级；
  • 禁止状态机——流程由 LLM 决策、不预先编码；
  • 禁止合成消息——所有对话均为真实角色对真实角色，UI 显示全部消息；
  • prompt 优先于宿主守门——LLM 决策类错误改 prompt，host-side 守门仅用于数据完整性与不可逆操作。

05九个 Agent 角色

OpenCorvus 暴露 9 个对外的专业 Agent。每个 Agent 在独立 LLM 会话中运行，持有独立 prompt cache 与工具集， 通过结构化结论（非 transcript）回传给 Orchestrator，避免主控上下文成本随子任务深度膨胀。 下图按职责将 9 个 Agent 分为三层；Orchestrator 居中通过工具调用辐射调度。

每个角色做什么

前置分析层（明确目标）

intent-analysis

Intent

用户最先遇到的角色。把“做个网页”这种模糊请求拆解为多目标、隐含约束、消歧问题。

requirements

Requirements

把意图转译为 REQ-1, REQ-2 … 的可枚举需求清单，并把基础技术决策（运行时、关键库）写入 Decision Log。

design-analyst

Design Analyst

可选环节。任务带有视觉参考（截图、参考网页）时，由它把图像证据翻译为 PRD / SPEC，避免后续 Agent 看图脑补。

主控与执行层

architect

Architect

关键角色。把需求分解为至少 2 个独立可执行的 Goal，并产出 ArchitectContractGraph——goal 之间的接口契约图。

orchestrator

Orchestrator

主控大脑。持有系统 prompt + 动态 describe 段，通过 requirements / architect / build / integrity / deliver 等工具调度其他 Agent。

build

Build

每个 Goal 一个独立 git worktree，由 Build Agent 调度外部执行器（mirrorcode / codex / claude-code）实现。

审计与对抗层（质量门）

integrity

Integrity

后期审计员。对 REQ 覆盖度、技术可行性、是否幻觉、方案质量做四维审查，不通过则提议修复（goal 级别）。

delivery

Delivery

纯评审视角的关卡：读所有验证证据、跑视觉验证、查测试，只发布 verdict（通过 / 拒绝 + 影响 goal），无修复权。

prosecutor

Prosecutor

对抗性评估器。专门寻找 Delivery 忽略的失败模式：可复现反例、未被指标覆盖的盲区，允许提议新的诊断指标。

Agent 间通信

OpenCorvus 不设全局消息总线。Agent 间的信息流通过三个真实通道：

  1. 工具调用与返回——Orchestrator 调用 architect / build 等工具，返回的结构化结论被嵌入主控对话历史；
  2. 持久化工件——goal、run、attempt、verdict 全部落入 engine_artifact，后续 Agent 通过查询工件读取上游产出；
  3. Decision Log——跨 Agent 共享的决策记录，承载“为什么”而非“做了什么”。

注：session.sql.ts 中 SessionKind 共 15 种；上述 9 个为对外暴露的专业 Agent， 另 6 种（root / gateway / goal / assistant / executor / system）为运行时容器，不作为角色暴露。 对话流不允许“仅给模型可见、不给界面可见”的合成消息——所有 agent 消息、tool result 在 UI 中必须可见。

06Goal 与契约：从需求到机器可验规约

OpenCorvus 在需求与实现之间引入两层结构化中间表示：Goal DAG（任务的可执行分解）与 Contract IR + ArchitectContractGraph（跨 Goal 的接口规约图）。两者的目的是把“模糊需求” 转换为“可独立验证、可机器审计、可局部回退”的工程对象。

为什么强制目标分解

单 Goal 实现端到端需求在工程上有三类问题：失败不可局部回退、跨模块接口形态滞后于实现暴露、风险与覆盖度无法分项度量。

因此 OpenCorvus 在 architect/output-tools.ts 的 submit_architect 工具里加了运行时校验 （常量 MIN_ARCHITECT_GOAL_COUNT = 2）：Architect 输出少于 2 个 goal 直接抛错， 必须显式声明 goal 间的接口契约。

Contract IR：让接口“机器可验”

Architect 不能只用自然语言说“这里返回一个股票数组”。它必须输出一个 Contract IR—— 由 Zod schema 定义的中间表示。看一个具体例子：

Contract IR 是一个判别式联合（discriminated union），三种形式：

  • type：结构体——含若干字段，每个字段都要声明值域（ValueDomain）；
  • function：函数签名——参数列表 + 返回类型；
  • enum：枚举——若干 variant 的闭集，每个 variant 含 value + meaning。

每个字段的值域有五种声明方式：open（未约束，必须给 justification）、literal_union、branded、numeric_range、ref。 源 packages/opencorvus/src/architect/contract-ir.ts

Contract Graph：goal 间的依赖 DAG

把多个 Contract IR 连接成图就是 ArchitectContractGraph：每个 contract 标注“谁生产”“谁消费”， 另有一组 dependency 边记录 goal 间的依赖原因（contract 引用 / 启动顺序 / 集成顺序）。 循环依赖、孤立消费者、引用未声明 contract 等错误在提交时拦截，而不是在 build 后才暴露。 源 packages/opencorvus/src/architect/contract-graph.ts

三段职责正交：Goal 描述意图、Contract Graph 规定接口、Runtime Artifacts 记录事实。 任一段都可被独立验证或回放，不在层间互相污染。

08验收评分：四族评分器

Architect 在每个 Goal 上挂载若干 Acceptance Spec。每个 spec 含一个或多个评分器 （scorers 是数组，schema 层校验最少 1 个）。评分器按求值机制分为四族， 适配从纯静态校验到主观语义评审的不同需求：

Family 1 · Shell

Heuristic 启发式

跑一条 shell 命令或脚本，exit_code = 0 即通过。适合 build、lint、test 这类外部工具。

Family 2 · LLM

LLM Judge 模型评审

把验收准则写成自然语言，配 2–5 级 rubric，由 LLM 序分。适合代码可读性、UI 是否符合参考图等主观维度。

Family 3 · Builtin

Prebuilt 预置评分

开箱即用的常见检查：factuality / relevance / contains / exact_match / length_within / json_schema。

Family 4 · AST

Contract Audit 契约审计

不调用 LLM。直接 AST 解析代码，对照 ContractIR 的 ValueDomain，看实际赋值是否越界。最快、最确定、最可复现。

严重度与触发时机

每个 Acceptance Spec 还要声明严重度（essential / important / optional / pitfall） 和触发时机（on_goal / on_delivery）。Delivery Agent 评审时按严重度阈值汇总： essential 全部通过才能放行。失败的 spec 会被打成结构化 verdict，回送给 Orchestrator 决定下一步——重试同一 plan，还是基于新事实 replan。 源 packages/opencorvus/src/acceptance/types.ts

09数据持久化：三层结构

OpenCorvus 不依赖远程数据库。每个项目目录下都有独立的 SQLite： <projectDir>/.opencorvus/opencorvus.db，开启 WAL 模式 + 外键约束。 所有 DDL 集中在 packages/opencorvus/src/storage/ddl.ts（单一来源，44 张表 / 虚拟表 / 索引集中维护）。 持久化按职责拆为三层：SQLite 关系层承载实体；append-only 事件层承载因果时序事实； 磁盘 worktree 层承载真实代码副本。三层通过 ID 串联但责权各异。

Append-only 不是 trigger 强制

engine_task / engine_goal 等“主体表”的 status / time_started 等字段仍允许更新； “append-only”是写入纪律——对 engine_artifact 和 protocol_event 这两类事实记录， Agent 们约定只追加新行、不修改旧行。由代码风格、单元测试和 reviewer 共同维护，不是数据库 trigger。

10事件驱动与唤醒

OpenCorvus 不维护后台轮询循环。任务推进由外部事件触发——任务创建、消息到达、子 Agent 完成、Eval 结果回流 均作为新事件写入 protocol_event，并触发对应任务的一次 wake：

  1. 用户通过 HTTP / Slack / TUI 发起任务，Engine 写入 engine_task，发布事件到 protocol_event。
  2. TaskQueueService（位于 packages/opencorvus/src/scheduler/）串行调度该任务的“唤醒”。
  3. Orchestrator 读完所有 append-only 事实，自行判断下一步该调度哪个工具。
  4. Agent 完成 / 外部消息到达 / Eval 结果回流 → 都是新事件，触发下一次唤醒。
  5. 当编排器决定 task done 或 budget exhausted，循环停止。

SSE：把事件推回前端

前端订阅 GET /task/<task_id>/events。SSE 路由在 server/routes/orchestrator.ts， 从 protocol_event 按 seq 单调拉取并流式转发；具体的事件查询函数 ProtocolStore.listTaskEventsAfter() 定义在 packages/opencorvus/src/protocol/store.ts。 断线时客户端会用最后看到的 seq 作为 cursor 重连——已序列化事件按 cursor 去重，不会重放； 非 sequenced 的 ephemeral 内部事件断线即丢，不影响最终状态投影。

$ curl -N http://127.0.0.1:7878/task/<task_id>/events

event: artifact.created
data: {"kind":"goal_run_attempt","goal_id":"g1",...}

event: agent.message
data: {"role":"architect","content":"..."}

event: task.completed
data: {"reason":"all_essential_passed"}

11前端 Overlay：Solid.js SPA 与多宿主

前端代码位于 packages/overlay/，技术栈 Solid.js + Vite 6 + Tauri 2。 选择 Solid 而非 React 的考量在于细粒度响应式（fine-grained reactivity）对流式事件场景的契合： 后端每推送一条 artifact 仅触发挂载到该 artifact 的组件局部重新求值，不进入 VDOM reconciliation。 对一个长时间在线、每秒接收多条 SSE 事件的前端，这是降低渲染开销的关键。

组件分组

packages/overlay/src/components/ 下约 75 个 .tsx 组件，按职责分为四大家族：

对话

Conversation 家族

Conversation / ChatBubble / ChatComposer / AgentSessionReplyBox——流式渲染 agent 消息、tool result、reasoning、附件。

任务

Task 家族

TaskList / TaskDetailOverlay / TaskStatusHeader / TaskProgressBar——左侧任务面板与详情视图。

布局

Panel 家族

Panel / Section / WorkspacePanel——右侧工作区视图（编辑器、diff、预览）。

对话框

Dialog 家族

AppDialogHost / SessionDialogHost / GoalDialogHost / ConfigDialogHost——权限确认、会话配置等模态。

状态分层

位于 packages/overlay/src/store/，9 个 store 文件分层职责，避免巨型 store： app.ts / board.ts / messages.ts / page-mode.ts / card-tree.ts / dialog.ts / settings.ts / reasoning.ts / conversation-ui.ts。

多宿主：Tauri & VS Code 共享业务逻辑

services/host-transport.ts 抽象了“前端到后端”的传输层。Tauri 桌面端通过 sidecar 直接访问本机端口；VS Code webview 通过 message channel 转发——业务代码不感知差异。

12执行器（Executor）

Build Agent 仅负责调度决策，真正的代码生成由 Executor 完成。OpenCorvus 提供一个内置默认实现，并允许通过 auto-discover 挂载外部编码 CLI。三种执行器并存且可指定：

Executor ID角色来源
mirrorcode 内置默认。无需外部 CLI，视觉参考页面复制、前端结构提取等场景的兜底执行器。 仓库自带
注实现位于 executor/opencorvus.ts；命名 mirrorcode 致敬血缘自 sst/opencode 的早期历史。
codex OpenAI Codex CLI 集成。集群服务模式。 外部安装 + auto-discover
claude-code Claude Code CLI 集成。本地或远程。 外部安装 + auto-discover

启用自动发现：

export OPENCORVUS_AUTO_DISCOVER_EXECUTORS=1

注册机制在 packages/opencorvus/src/executor/registry.ts：

  • ExecutorRegistry.registerCoding(name, provider, options) 注册外部执行器；
  • ExecutorRegistry.createInstance(name) 每个 goal 拿独立实例，状态隔离；
  • ExecutorRegistry.requireCoding(name) Build Agent 在取 provider 时调用—— 如果未发现到 codex / claude-code，直接抛 ExecutorNotConfiguredError，对应 goal 的 build 立即失败，不会静默 fallback 到 mirrorcode。

指定 codex 或 claude-code 但未发现可用 CLI 时直接拒绝任务创建，不会静默回退到 mirrorcode。 这符合项目第二条设计红线：失败应在 task 创建点暴露，而非在 verification 阶段才被发现。

15设计取舍（Why not X）

本节列出若干常见疑问对应的设计决策——这些决策都是“主动选不做”的结果，比正向陈述更能说明项目的判断标准。

为什么不让一个全能 Agent 干完所有事？
单 Agent 的上下文窗口虽大，但注意力不大。任务越长、上下文越满，模型越容易“忘记早期约束”。 把它拆成 9 个角色，每个角色只看自己需要的输入（结构化 conclusion 而非原始 transcript），单角色上下文短，注意力集中。
为什么用 SQLite 而不是 Postgres / 云数据库？
OpenCorvus 是“你的本地仓库 = 完整运行时”。SQLite 无服务、零配置、单文件可备份。 多任务并发由 TaskQueueService 串行调度 + SQLite WAL 并发读协调，单机性能足够。
为什么禁止状态机？我看好多 agent 框架都有 state graph。
状态机的本质是“预先规定流程”。但 OpenCorvus 的核心命题恰恰是“让 LLM 根据当下事实做决定”—— 如果你已经知道“接下来必然是 A 然后 B”，那这个流程不需要 LLM；如果你不知道，那写 state graph 就是用代码冒充智能。
为什么 prompt 优先于宿主守门？让代码直接拦截不更稳吗？
在“LLM 选错工具 / 走错路径”这类场景里，宿主层加 if 守门看似稳，实则把“教模型走对路”的责任埋进了代码，调 prompt 就调不动了。 数据完整性（Zod schema、DB constraint）和不可逆操作的二次确认仍走宿主——这是两类合理场景。
为什么前端选 Solid 而不是 React？
Solid 的细粒度响应式让流式更新的渲染开销远低于 React VDOM reconciliation。 OpenCorvus 前端是一个长时间在线、每秒收到多条 SSE 事件的应用，渲染性能是体验底线。 Solid 官方文档明确其 API 与 React Hooks 心智接近，已有 React 经验的工程师过渡成本可控。
那为什么不做云托管版？
能做，但暂不做。开源版的目标是“你的代码、你的 worktree、你的密钥不离开你的机器”。 云托管会立刻引入 secrets 管理、多租户隔离、SOC2 等不属于“让 Agent 团队跑起来”这一核心问题的复杂度。

16结语

OpenCorvus 的工程命题是：当前 LLM 的生成能力已经足够，制约可交付性的是工程纪律—— spec 化、契约化、可独立验收化、可审计化。这些纪律在 prompt 层难以稳定兑现， 因此本项目将其下沉到框架层，通过多 Agent 流水线、机器可校验契约、append-only 事件序列、自动 replan 闭环来强制落地。

由此衍生的关键设计选择：

  • 事件驱动而非后台轮询——任意时刻的状态都是事件序列的投影，进程崩溃可重建；
  • append-only artifact 而非 mutable state——审计踪迹与决策回放与生成结果天然解耦；
  • 9 个独立会话 Agent 而非单一全能 Agent——单角色上下文短、注意力集中、子任务可独立 retry；
  • Contract IR + Goal DAG 替代模糊自然语言 spec——验收可机器化、跨模块接口先于实现固化；
  • 五条设计红线（禁双源 / 禁 fallback / 禁状态机 / 禁合成消息 / prompt-over-host）——保持代码库单一来源与决策可读性；
  • Solid.js + Tauri + SQLite + WAL 的本地优先栈——单文件可备份、无云依赖、零部署成本。

本白皮书所述机制均已在仓库中可被代码路径与单元测试佐证；未来版本的演进方向、未解决的工程问题与公开 roadmap， 以 GitHub 仓库 issue / discussion 为准。
