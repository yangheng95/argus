基于以下 PRD，交付一个“可运行、可验证、范围收敛”的 Moment Diary 后端 MVP。

这是一个 backend-first 的实现任务，不要求移动端或完整 Web UI，但交付物必须能作为后续前端接入的稳定 API 与数据层基础。

## 目标

围绕 `specs/prd.txt` 的 MVP 范围，交付一个 Bun + TypeScript + Hono + SQLite 的最小可用后端，满足以下核心能力：

1. 用户可以注册和登录。
2. 用户可以创建、读取、更新、删除日记。
3. 日记支持正文、心情、标签、创建时间、更新时间。
4. 可以按时间倒序浏览时间轴。
5. 可以按标签或心情筛选。
6. 必须体现基础隐私与安全设计：密码不能明文存储，受保护接口不能匿名直接写入/读取他人数据。

## 范围约束

只做 backend-first MVP，拒绝做这些内容：

- 不做移动端 UI、网页页面、精美前端。
- 不做社区、多人协作、订阅付费、AI 陪聊、复杂统计报表。
- 不做图片/语音/位置/天气的完整上传链路。
- 不做伪装入口、Face ID、云同步等依赖外部平台的能力。

如果 PRD 中还有更大范围内容，请主动收敛到“最小但合格的后端 MVP”。

## 技术要求

- 使用 TypeScript。
- 使用 Hono 作为 HTTP API 框架。
- 使用 SQLite 做本地持久化。
- 可以自由补充必要依赖，但不要引入明显过重的框架。
- 代码结构要清晰，避免把所有逻辑塞进单文件。

## 建议交付结构

不要求完全一致，但至少应有这些层次：

- `src/` 下的应用入口
- 路由层
- 数据库 schema / 初始化逻辑
- 领域或 service 层
- 测试文件

## 核心数据模型

至少实现以下模型或等价结构：

### User

- `id`
- `email`
- `password_hash`
- `created_at`

### DiaryEntry

- `id`
- `user_id`
- `title`（可选）
- `content`
- `mood`（可选）
- `created_at`
- `updated_at`
- `is_favorite`（可选，默认 false）

### Tag

- `id`
- `name`

### DiaryTag / 关联关系

- `diary_id`
- `tag_id`

## API 要求

至少实现这些接口或语义等价接口：

### 认证

- `POST /auth/register`
- `POST /auth/login`

可以使用简化 token 机制，但必须满足：

- 登录后返回可用于后续请求的认证信息
- 受保护接口要校验认证身份
- 不允许一个用户读取或修改另一个用户的日记

### 日记 CRUD

- `POST /diaries`
- `GET /diaries`
- `GET /diaries/:id`
- `PATCH /diaries/:id`
- `DELETE /diaries/:id`

### 浏览 / 回顾

- `GET /timeline`

要求：

- 时间轴按创建时间倒序返回
- 支持按 `tag` 和 `mood` 过滤中的至少一种，最好两种都支持

## 业务规则

- 创建日记时，`content` 不能为空。
- 标签可以去重。
- 更新日记时必须刷新 `updated_at`。
- 删除日记后，其标签关联关系不能残留为脏数据。
- 返回结构要稳定、可测试，不要随意混入调试字段。

## 测试与验收

必须编写自动化测试，至少覆盖这些场景：

1. 用户注册成功，密码不是明文存储。
2. 用户登录成功，并可携带认证访问受保护接口。
3. 创建日记成功，并能正确返回内容、心情和标签。
4. 时间轴按时间倒序返回。
5. 按标签或心情筛选可用。
6. 用户不能访问其他用户的日记。
7. 更新日记会刷新 `updated_at`。
8. 删除日记后，读取失败且关联关系被清理。

## 交付标准

你的交付必须满足：

- 项目能通过 TypeScript 类型检查。
- 自动化测试通过。
- 代码不是只有脚手架或占位。
- 不新增无关 README、文档、演示页面或噪音文件。

## 实施原则

- 先收敛范围，再实现。
- 先保证可运行、可测、可维护，再考虑扩展性。
- 不要输出长篇方案文档来替代实现。
- 遇到不明确的细节时，采用最合理、最小化、可测试的默认方案并继续执行。
