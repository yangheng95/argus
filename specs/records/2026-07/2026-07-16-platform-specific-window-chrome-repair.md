## Root cause

The previous repair made `decorations: true` a global window setting. That does produce AppKit traffic lights on macOS, but on Windows and Linux it asks Win32/GTK to add a complete system titlebar around an application that already owns a complete HTML titlebar. The double titlebar is therefore a deterministic ownership error, not a per-platform spacing bug.

The macOS geometry was also hard-coded as `trafficLightPosition: { x: 14, y: 12 }`. Tauri documents that overlay-titlebar height differs by macOS version; the supplied screenshot confirms that overriding AppKit's placement does not align with this compact row. The correct geometry source is AppKit's default traffic-light layout.

## Implementation plan

1. Restore the main window's shared configuration to frameless ownership (`decorations: false`) and remove the traffic-light coordinate override. Retain the macOS-only hidden/overlay titlebar intent, then enable decorations in Rust only under `#[cfg(target_os = "macos")]`.
2. Restore one `WindowControls` component for Tauri builds whose compile target is not macOS. Keep minimize/maximize state in that component, reuse the existing transport handle, and route close through the shared close-confirmation function.
3. Keep the macOS leading inset tied to explicit Tauri-host and build-target evidence. Restore the titlebar's third grid column and dedicated mature Button primitive styles only for the mutually exclusive Windows/Linux component.
4. Replace the prior all-native tests with a platform ownership matrix: public config is frameless, Rust enables decoration only on macOS, traffic-light coordinates are absent, Windows/Linux controls are compile-target scoped, browser/VS Code are excluded, and both close entry points share cleanup.
5. Build and inspect the real frontend titlebar in isolated Node/browser sessions for macOS content geometry and the Windows/Linux control surface. Do not claim a native AppKit/Win32 end-to-end screenshot without launching a native process; native process restart remains outside the granted runtime boundary.

## Codex review feedback

The earlier plan treated “native window controls” as one cross-platform implementation property. Review against the user's Windows screenshot invalidates that assumption: the application titlebar is itself a platform chrome owner, so enabling native decorations everywhere violates single ownership. The revised model selects ownership at compile time: AppKit on macOS; the existing frameless application chrome on Windows/Linux.

## Outcome

- The shared Tauri window is frameless again. Rust enables decorations and `TitleBarStyle::Overlay` only inside `#[cfg(target_os = "macos")]`, so Windows/Linux cannot receive a second native titlebar.
- The hard-coded `trafficLightPosition` override is gone. AppKit now owns traffic-light style and placement; the HTML row reserves one fixed logical-pixel token that does not grow with application zoom.
- Windows/Linux regain one compile-target-scoped `WindowControls` component using the current shared 32-pixel Button primitive. Browser, VS Code, and macOS builds cannot render this component. Native close/Alt+F4 and the application close button share `confirmOverlayWindowClose` and the existing `window.quit` cleanup path.
- Passed 21 focused source/behavior tests, Overlay TypeScript, panel i18n, Vite production build, Prettier, Rust compilation, and all 30 Rust tests. Rust emitted one existing macOS dead-code warning for `create_taskbar_badge_icon`.
- A Node-served real application page was opened in the controlled browser and personally inspected. The titlebar measured 36 pixels high across 1280 pixels, kept File/Edit/View/Help aligned, and rendered zero desktop controls in the browser host; the screenshot showed no extra titlebar or reserved control gap.
- Native AppKit/Win32/GTK chrome cannot be composited into the browser screenshot. The macOS ownership path was compiled on macOS and verified against Tauri/TAO source; Windows/Linux ownership is covered by the mutually exclusive source/configuration contract. A packaged Windows/Linux screenshot remains platform acceptance evidence rather than being misrepresented as a browser end-to-end result.
