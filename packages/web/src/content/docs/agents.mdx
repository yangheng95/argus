OpenCorvus's orchestration is built around **agents**. The agent registry — names, modes, default prompts, tool whitelists, permission rulesets — lives in `packages/opencorvus/src/agent/agent.ts` (`Agent.state()`).

## Built-in agents

The registry currently ships with the agents below. `mode` controls how the agent is invoked: `primary` runs as the top-of-stack agent in a session; `subagent` is dispatched by another agent via the `task` tool. Agents marked `hidden` are routing slots — not selectable from the picker, but their model / prompt can still be overridden in config.

| Agent          | Mode             | Purpose                                                                                                                                                                                                                                          |
| -------------- | ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `coding`       | primary          | Interactive coding agent for ordinary local sessions.                                                                                                                                                                                            |
| `build`        | primary (hidden) | Implementation agent. Executes read / edit / bash-style implementation tools when dispatched by the orchestrator or direct workflow.                                                                                                             |
| `visual-qa`    | primary (hidden) | Visual QA stage agent with a fixed visual evidence tool surface.                                                                                                                                                                                 |
| `general`      | subagent         | General-purpose multi-step research / parallel-work agent. Dispatched via the `task` tool.                                                                                                                                                       |
| `explore`      | subagent         | Codebase exploration — fast file / code search, read-only by default.                                                                                                                                                                            |
| `orchestrator` | primary (hidden) | Orchestrator agent. Owns task lifecycle decisions, dispatches workers through `dispatch_agent target=...`, and mutates task / goal lifecycle through `manage_task action=...` such as `action=modify_goal` and `action=propose_task`. |
| `requirements` | primary (hidden) | Requirements stage. Extracts user requirements and foundational technical decisions.                                                                                                                                                             |

Other registered agents (`architect`, `frontend-design`, `frontend-research`, `intent-analysis`, `integrity`, `fact-check`, `deep-research`, `goal-workload-analyst`, `summary`, `title`, `compaction`, `mission`, `control`) are stage / utility slots invoked internally by the orchestrator, mission runtime, or session loop. They surface in config (model + prompt overrides) but are not user-selectable unless a dedicated runtime exposes them.

See `packages/opencorvus/src/agent/agent.ts` for the canonical definitions.

## Sub-agent dispatch

Sub-agents are dispatched via the **`task`** tool from ordinary sessions, or by the orchestrator through `dispatch_agent target=...` for workers such as `requirements`, `architect`, `build`, `integrity`, `frontend_design`, and `frontend_research`. Each dispatch creates its own worker session.

When the orchestrator runs the `pipeline` workflow, the Architect creates goals, each blocking goal is built in an isolated worktree, and `integrity` performs the final task-level review.

## Per-agent model

Each agent's model is set under `agent.<name>.model` — see `packages/opencorvus/src/config/config.ts` (`agent` is `z.object({...}).catchall(Agent)`). The related `assistant.<name>` blocks are described in the same config schema.

```jsonc
{
  "agent": {
    "build": { "model": "anthropic/claude-sonnet-4-6" },
    "frontend-design": { "model": "anthropic/claude-sonnet-4-6" },
  },
}
```

For agent names containing a hyphen (`frontend-design`, `intent-analysis`) the JSON key must be quoted: `"frontend-design"`.

## Defining a custom agent

You can define agents inline in your config or as markdown under `~/.config/opencorvus/agents/` or `.opencorvus/agents/`:

```jsonc
{
  "agent": {
    "code-reviewer": {
      "description": "Reviews code for best practices and potential issues",
      "model": "anthropic/claude-sonnet-4-6",
      "prompt": "You are a code reviewer. Focus on security, performance, maintainability.",
      "tools": { "write": false, "edit": false },
    },
  },
}
```

Custom agents inherit the default permission ruleset (built up in `Agent.state()` from the `defaults` block at `agent.ts`).

## Default agent

Set `default_agent` to pick the agent used when none is specified explicitly. Must be a primary, non-hidden agent — `Agent.defaultAgent()` (`agent.ts`) rejects subagent / hidden choices.

## Agent budgets

Per-agent step budgets and skill paths live under `assistant.<name>` (config.ts):

```jsonc
{
  "assistant": {
    "requirements": { "max_steps": 20 },
    "architect": { "max_steps": 40 },
    "frontend_design": { "max_steps": 30 },
    "intent_analysis": { "max_steps": 10 },
    "build": { "max_steps": 80 },
    "integrity": { "max_steps": 160 },
  },
}
```

Top-level orchestrator budgets sit directly on `assistant` (config.ts):

- `assistant.max_runs` — maximum total task runs
- `assistant.max_fix_runs` — maximum fix runs after failure
- `assistant.max_executor_groups` — maximum parallel executor groups

These are hard ceilings to prevent runaway loops. See [config](/docs/config/).
