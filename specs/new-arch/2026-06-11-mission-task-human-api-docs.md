# Mission and Task human API docs

Date: 2026-06-11

## Problem

`packages/web/src/content/docs/{zh-cn/,}reference/api.mdx` is generated from `packages/sdk/openapi.json` and intentionally lists operations as a compact table. It is correct as an operation index, but it is not the right surface for humans integrating the server around Mission and Task workflows. The most common path needs narrative docs: start or resume a Mission, create a Task, observe status, send follow-up input, and download the resulting project archive.

## Call-point inventory

Full-repo grep before writing this plan:

| Surface | Evidence | Decision |
| --- | --- | --- |
| Generated API reference | `packages/web/src/content/docs/zh-cn/reference/api.mdx` and `packages/web/src/content/docs/reference/api.mdx` are generated by `packages/opencorvus/script/docs/render-api-md.ts`. | Do not hand edit generated pages. Link to them as the exhaustive operation list. |
| Web docs sidebar | `packages/web/astro.config.mjs` `sidebar` has `Reference` items. | Add a single `reference/mission-task` page to the existing Reference group so both locales resolve. |
| Task routes | `packages/opencorvus/src/server/routes/orchestrator.ts` defines `task.create`, `task.list`, `task.get`, `task.status`, `task.projectArchive`, `task.message`, `task.events`, `task.cancel`, `task.retry`, and `task.replan`. | Document the common integration path and point to API reference for the full route inventory. |
| Task input schema | `packages/opencorvus/src/engine/model.ts` defines `CreateTaskInput`. | Explain stable fields and use SDK examples instead of duplicating the full generated schema. |
| Task status schema | `packages/opencorvus/src/status/task-status-snapshot.ts` defines `TaskStatusDetail`. | Document normalized `status`, lifecycle `lifecycleStatus`, and progress details. |
| Task archive route | `packages/opencorvus/src/server/routes/orchestrator.ts` `task.projectArchive` returns `application/zip` with content-disposition, content-length, and file count headers. | Include a download example and the Git worktree 422 case. |
| Mission routes | `packages/opencorvus/src/server/routes/mission.ts` defines `mission.list`, `mission.wake`, `mission.status`, `mission.rename`, `mission.abort`, and `mission.delete`. | Document Mission as a long-running coordinator session, not a parallel task engine. |
| Mission session source | `packages/opencorvus/src/mission/session.ts` pins one `kind="mission"` session per `(project, missionID)`. | Explain `missionID` creation/resume semantics and session backing. |
| Mission task provenance | `packages/opencorvus/src/engine/store.ts` `listMissionTasks` reads task metadata mission provenance. | Explain that Mission dispatches work as normal Tasks and status aggregates those Tasks. |
| SDK client behavior | `packages/sdk/js/src/client.ts` handles `directory`, Basic Auth, and generated methods. | Prefer SDK examples for typed integration; include curl for protocol clarity. |
| Sidebar health | `packages/web/astro.config.mjs` still referenced removed or absent docs: `tui`, `themes`, and `keybinds`; `specs/new-arch/2026-06-10-tui-removal-plan.md` says docs should remove TUI surface. | Remove stale sidebar items while adding the new Mission/Task reference page so web docs build can validate the docs tree. |

## Required end state

1. Add a human-readable Mission and Task API guide in both web docs locales.
2. Keep `packages/sdk/openapi.json` and generated `reference/api.mdx` as the machine/exhaustive source.
3. Cover publish task, query status, download code, Mission wake/list/status, auth, project directory, SDK examples, and raw HTTP examples.
4. Verify docs generation still matches the generated API reference and the web docs build accepts the new page.

## 2026-06-11 review feedback

The first Chinese draft was still shaped like an endpoint inventory and was too abstract for a human integrator. The revised Chinese page now starts with a complete runnable SDK script, then explains Task and Mission flows with direct SDK and curl examples for create, status polling, message input, archive download, Mission wake, Mission status, and Mission management.

## Non-goals

This change does not alter route schemas, SDK generation, task execution, Mission execution, or OpenAPI rendering.
