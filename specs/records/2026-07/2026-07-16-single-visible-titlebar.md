## Root cause

The second repair solved Windows/Linux ownership but initialized macOS in the wrong order. The main window was constructed with `decorations: false`, so its WebView content layout was established as frameless. The `setup` callback then added decorations and requested `Overlay`. The screenshot proves that this runtime mutation produced an AppKit titlebar above the existing HTML row instead of extending the content view under the titlebar.

This is different from the first all-decorated build, where macOS received `decorations: true`, `hiddenTitle: true`, and `Overlay` during window construction and the traffic lights occupied the HTML row. The correct fix is therefore construction-time macOS overlay, not another coordinate adjustment.

## Implementation plan

1. Create the configured window hidden with decorations enabled so macOS receives the complete AppKit overlay/full-size-content builder path.
2. In `setup`, remove decorations only under `#[cfg(not(target_os = "macos"))]`. Do not mutate macOS decorations or titlebar style at runtime.
3. Size and position the still-hidden window, then reveal it once through the existing `show_window` helper. This prevents Windows/Linux from ever painting the temporary construction decoration.
4. Keep the existing mutually exclusive application controls: they render only for non-macOS Tauri builds, while AppKit traffic lights overlay the same HTML row on macOS.
5. Rewrite the platform ownership regression to assert construction-time overlay, non-macOS decoration removal, hidden startup, and one final reveal. Re-run focused tests, TypeScript, Vite, Rust, documentation health, and a real browser screenshot of the application titlebar.

## Codex review feedback

The previous plan correctly rejected global visible native decorations but incorrectly assumed that applying macOS decorations in `setup` was equivalent to constructing an overlay window. Tauri's builder source and the user's screenshot disprove that equivalence. The revised design establishes native overlay geometry at construction and makes the window invisible until non-macOS decoration removal is complete.

## Outcome

- The main window is now constructed hidden with `decorations: true`, `hiddenTitle: true`, and `titleBarStyle: Overlay`. macOS therefore receives AppKit's full-size-content overlay path before the WebView layout exists; no runtime code adds an AppKit row afterward.
- The `setup` callback removes decorations only for non-macOS targets while the window is hidden, applies the existing size/position contract, and then calls the existing `show_window` helper once before backend startup. Windows/Linux cannot paint the temporary construction decoration, the main window is not delayed by backend startup, and the established application controls remain in the sole HTML titlebar.
- The previous macOS runtime `set_decorations(true)` and `set_title_bar_style` calls were deleted. No platform-specific duplicate `app.windows` configuration or coordinate override was introduced.
- Passed 21 focused window/titlebar tests, Overlay TypeScript, panel i18n, Vite production build, Rust compilation, and all 30 Rust tests. Rust emitted only the existing macOS dead-code warning for `create_taskbar_badge_icon`.
- A Node-served real application page was opened in the controlled browser and personally inspected. It contained exactly one `header.titlebar`, measured from `top: 0` to `bottom: 36` across 1280 pixels, and kept navigation plus File/Edit/View/Help on that row. The screenshot showed no fabricated or stacked application titlebar.
- The user's running native Overlay was not restarted or refreshed. Browser evidence is not represented as native AppKit/Win32/GTK end-to-end evidence; the native repair is verified by Tauri construction order, the compiled macOS Rust path, and the platform ownership regression until a new package is launched on each target platform.
