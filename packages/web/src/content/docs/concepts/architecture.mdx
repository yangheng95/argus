OpenCorvus's job is to turn a natural-language request into verified code changes. The current architecture is orchestrator-led: the orchestrator reads the task snapshot on every wake, chooses explicit workflow tools, and records durable evidence as SQLite rows and artifacts.

For a click-through source map of the current runtime, see [Enterprise architecture explorer](./enterprise-architecture.md).

## HTTP API Runtime Layering

The HTTP server (`packages/opencorvus/src/server/server.ts`) splits routes into two real layers:

- **Control plane** — `/global/*`, `/auth/*`, `/ui/*`, plus `/log`, `/shutdown`, `/restart` are mounted before the `Instance.provide` middleware. They work even when no project directory is open.
- **Project-scoped** — routes that operate on the active workspace (`/tasks`, `POST /task`, task writes, `/session`, `/run`, `/mcp`, `/experimental`, `/panel`, `/pty`, ...) run inside `Instance.provide({ directory, init: InstanceBootstrap })`. They require a project directory from `?directory=` or `x-opencorvus-directory`.
- **Task-record reads** — `GET /task/{taskID}` and the task record routes `/status`, `/board`, `/progress`, `/events`, `/brief`, `/transcript`, `/runs`, `/interactions`, `/bindings`, `/operator-model-context`, and task conversation reads resolve ownership from the task record. They do not require `directory`.

Route handlers do not read `process.env`, open SQL tables directly, or use `z.any()`. `bun run api:routes-check` protects that boundary, and `bun run docs:api` regenerates the web API reference from OpenAPI.

## Workflow Shape

OpenCorvus has two built-in workflows in `packages/opencorvus/src/engine/workflow.ts`:

| Workflow   | Shape                                                                                                                      | Use case                                                                                   |
| ---------- | -------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| `direct`   | `analyze_intent` as needed, then `build`                                                                                   | Explicit `kind=build`, scoped edits, bug fixes, short debugging                            |
| `pipeline` | `(frontend_design / frontend_research as needed) → analyze_intent → requirements → architect → per-goal build → integrity` | Multi-file features, UI replication, refactors, tasks needing explicit acceptance evidence |

The workflow definition is prompt context for the orchestrator. The orchestrator can skip optional steps or reroute based on evidence. `integrity` is the final session-bound review step for the pipeline.

## Runtime Layers

```
User request
  ↓
Channel / UI / API
  ↓
Engine task row
  ↓
Orchestrator session
  ├─ typed workflow tools: requirements / architect / build / integrity / ...
  ├─ durable artifacts: runs / goal_run_attempts / verification evidence / integrity attempts / reports
  └─ explicit user interactions: questions and permissions
  ↓
Worker sessions
  ├─ requirements, architect, frontend-design, frontend-research
  ├─ per-goal build sessions in isolated worktrees
  └─ integrity review session
```

## Responsibilities

| Component     | Role                                                                                                               | Current source                                                                                   |
| ------------- | ------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------ |
| Channel / API | Converts external input into task creation, messages, and control operations                                       | `packages/opencorvus/src/channel/ingress.ts`, `packages/opencorvus/src/server/routes/`           |
| Engine        | Stores tasks, specs, requirements, goals, plan versions, artifacts, interactions, and projected status             | `packages/opencorvus/src/engine/engine.sql.ts`, `packages/opencorvus/src/engine/store.ts`        |
| Orchestrator  | Single task-level decision maker. Reads `describeTask`, dispatches typed tools, and decides recovery from evidence | `packages/opencorvus/src/orchestrator/agent.ts`, `packages/opencorvus/src/orchestrator/tools.ts` |
| Workflow      | Declares built-in `direct` and `pipeline` recommendations and renders progress from artifacts                      | `packages/opencorvus/src/engine/workflow.ts`                                                     |
| Build agent   | Implements direct tasks or one architect-authored goal in an isolated workspace                                    | `packages/opencorvus/src/build/agent.ts`                                                         |
| Integrity     | Final system review for pipeline tasks; returns pass/non-pass evidence to the orchestrator                         | `packages/opencorvus/src/integrity/`                                                             |

## Two Loops

### Outer: Orchestrator Wake Loop

`runTaskLoop` (`packages/opencorvus/src/orchestrator/loop.ts`) serializes wakes for one task and calls `Orchestrator.processTask`. Each wake reads the current describe/artifact snapshot and decides the next tool call.

### Inner: Session Agentic Loop

`SessionLoop` (`packages/opencorvus/src/session/loop.ts`) runs every worker session:

```
LLM emits tool call → tool executes → tool result is appended → next model turn
```

Typed orchestrator tools create worker sessions for requirements, architect, build, integrity, and related stages.

## Worktree Parallelism

Architect-authored goals are persisted in `engine_goal`. A per-goal `build` dispatch creates an artifact-backed goal run attempt (`engine_artifact.kind="goal_run_attempt"`) with its own workspace metadata. Goal status shown in the UI is derived from the latest goal-run attempt chain.
