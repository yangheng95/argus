## 性能修复 2026-04-10

用户反馈 overlay 长时间运行后越来越卡。诊断结论：dev-error 弹窗 + computeAgentCards 副作用 + _agentMsgCache 三层叠加的 CPU/内存累积。

### 排查过程

1. 先 recall 之前 commit `2741ab8e0` 的修复（_agentMsgCache cache key 稳定 / MutationObserver rAF dedup / _pendingParts TTL / flushAgentEvents Map merge / conversationMessages fingerprint）—— 验证全部仍然在原状，没被回退。
2. 用户提示 "是不是 dev errors 窗口" → 命中本质问题。`utils/dev-error.ts` 累积无界 + 内嵌的 11 个 devWarn/devError 全部在 createMemo body 内被 SSE 高频触发。
3. 副带发现 `_agentMsgCache` 也有累积 leak（pruneAgentEvents 限制 store.agentEvents 但不同步清 cache）。

### 根本问题（按因果链）

```
用户的根本反馈: overlay 越来越卡
    ↓
表象: DOM 节点持续增长 + listener 累积
    ↓
直接原因: dev-error.ts 没有上限，每条 entry 一个 listener + innerHTML + filter() O(n)
    ↓
驱动力: computeAgentCards / buildUserContextMessages 在 createMemo body 调用 devWarn
    ↓
触发频率: SSE 流式更新 → memo 每 16ms 重算 → 每次重算 push N 条 dev warn
    ↓
本质问题: createMemo 必须是纯函数。在 memo body 写副作用，是把"计算"和"日志"耦合，
            驱动频率被 SSE 速率劫持，无法控制。
```

### 修复（三层都修，不能只修一层）

**PERF-A: 加固 dev-error.ts** (`packages/overlay/src/utils/dev-error.ts`)

| 改动 | 修复的反模式 |
|---|---|
| ring buffer `MAX_DEV_ENTRIES = 200` | 无上限累积 |
| `${level}:${location}:${message}` 作 key 的 dedup map | 重复 entry 各占独立 DOM 节点 |
| listEl 一个 click handler 通过 `data-key` 委托 | 每条 entry 一个 closure listener |
| `textContent` + DOM API 替代 `innerHTML` | innerHTML HTML parser 开销 + XSS 表面 |
| 增量 `errorCount` / `warnCount` 维护 | 每次 push 都 `entries.filter().length × 2` 的 O(n) 退化 |
| `import.meta.env.DEV` 守卫 | prod build 也创建 DOM 的语义陷阱 |

prod 模式下 `devWarn` / `devError` 只调 `console.warn` / `console.error`，**完全不创建 DOM**。

**PERF-B: 删除 11 处 createMemo body 内的 devWarn/devError**

| 文件 | 删除处数 | 全部理由 |
|---|---|---|
| `packages/overlay/src/store/messages.ts` | 8 (computeAgentCards 内) | 全是"持续状态检查"而非真异常（goalInfo 还没填、sessionID 还没到、startTime 临时缺失），被 SSE 速率驱动反复 fire |
| `packages/overlay/src/utils/conversation.ts` | 3 (buildUserContextMessages 内) | 时间戳缺失的 fallback 警告，紧邻代码已经 fallback 到 Date.now() / 0，功能不受影响 |

**关键设计原则**：functional fallback **保留**（fallback 到 Date.now() 等代码不变），只删 warning 副作用。这不是无脑删——真正的数据完整性检查应该在 mutation 时（`setMessages` / `appendAgentEvent` / `setBoard`）做，而不是在派生层 memo 里 warn 个寂寞。

**PERF-C: 修 _agentMsgCache 累积 leak** (`packages/overlay/src/store/messages.ts`)

之前 commit `2741ab8e0` 把 cache key 改稳定（`msgID:kind`，不再每个 token 创建新条目）但**没有驱逐机制**。`pruneAgentEvents` 把 `store.agentEvents` 限制在每 stage 12 条，被 prune 出去的 event 在 store 里没了，**cache 还持有 msg 引用**。仅 `clearAgentEvents()`（task 切换）时清空。长任务持续运行时 cache 单调增长。

修复:
1. 抽出 `agentMessageStableKey(event)` helper —— 单一公式来源，避免 prune 时和 agentMessage 时算的 key 漂移
2. **关键**：把 `agentMessage` 中 `agentEventTime(event) || Date.now()` 的 fallback 改为**确定性的** `agentEventTime(event) || 0`。Date.now() 每次不同会让 stableKey 不稳定，prune 计算出来的 key 跟原来的对不上，清不掉 → leak 仍在
3. `pruneAgentEvents` 末尾用同样的 helper 算出 kept 的 stableKey set，从 `_agentMsgCache` 删除所有不在 set 里的条目

复杂度：cache 操作 O(n + m) 其中 n 是 cache size，m 是 kept events count（≤ 12 × stages 数）。可忽略。
