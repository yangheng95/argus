# Browser MCP Node Package Manifest

## Recall

- User request: explain and fix why `bun run build:overlay` produced an embedded sidecar where browser MCP failed with missing `browser-mcp-node/package.json`.
- Acceptance criteria:
  - `bun run build:overlay` / `bun run build --overlay-server` produces an embedded sidecar payload where `browser-mcp-node` is a complete packaged Node runtime root.
  - `browser-mcp-node/package.json` exists before Tauri embeds the sidecar archive.
  - Packaging and embedded-payload tests fail if the browser MCP runtime manifest is missing.
  - The fix does not make runtime package resolution fall back to a parent directory or source dependencies.
- Hard constraints:
  - No fallback or compatibility lookup from `browser-mcp-node` to the parent sidecar directory.
  - No disabling browser MCP to hide the packaging defect.
  - No restart, kill, refresh, or other interference with the user's running OpenCorvus / overlay process.
  - Do not revert or overwrite unrelated dirty worktree changes.
- Disk records read before implementation:
  - `specs/README.md`
  - `specs/records/2026-06/README.md`
  - `specs/records/2026-06/2026-06-29-subagent-infrastructure-homogeneity.md`
  - `specs/records/2026-06/2026-06-29-codex-app-server-mcp-env-toml.md`
- Whole-repository grep evidence:
  - `browser-mcp-node` appears in the overlay-server build scripts, browser runtime resolver, browser MCP launcher, Tauri `build.rs`, and packaging tests.
  - `runtimePackageRequireForExecPath` resolves `package.json` from `path.dirname(process.execPath)`.
  - The overlay Tauri embedded-payload tests check `browser-mcp-node/browser.mjs`, `node.exe`, and nested Playwright package manifests, but not `browser-mcp-node/package.json`.
  - The build scripts write `dist/<artifact>/package.json` only for the parent sidecar directory; they do not write a manifest for `dist/<artifact>/browser-mcp-node/`.
- Independent agent feedback: none; the user asked for direct clarification/fix, and the local DB, filesystem, and source evidence already identified the root cause.

## Root Cause

The overlay build is a unified embedded binary pipeline, but it embeds the sidecar directory exactly as generated by the OpenCorvus overlay-server build. That generated directory contains a parent `package.json`, plus `browser-mcp-node/browser.mjs`, `browser-mcp-node/node.exe`, and `browser-mcp-node/node_modules/**`.

The browser MCP server is launched by `browser-mcp-node/node.exe`, so `process.execPath` points inside `browser-mcp-node`. `runtimePackageRequireForExecPath(...)` correctly requires a colocated `package.json` beside that executable. The packaging defect is that `browser-mcp-node/package.json` is never written.

Runtime fallback to the parent sidecar manifest would reintroduce ambiguous dependency roots. The correct single-source fix is to make the browser MCP runtime directory complete at build time.

## Plan

1. Add one build-script helper that writes a minimal packaged runtime `package.json` into a supplied output directory.
2. Use it for both the parent sidecar directory and the nested `browser-mcp-node` runtime directory in `build.ts` and `build.local.ts`.
3. Add tests that assert both build scripts write the nested browser MCP manifest and that Tauri embedded-payload validation requires it.
4. Update the June records README index.
5. Run targeted packaging tests and spec health checks.
