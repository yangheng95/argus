OpenCorvus 调度架构图

这页不是全系统总览，而是专门讲清楚 OpenCorvus 的任务调度骨架： 谁创建任务、谁做生命周期决策、sub-agent 如何被调度、build 如何落到 executor， 以及 skill / MCP / plugin / ACP 这些基础设施分别接到哪一层。

当前现状 以 packages/opencorvus/src 当前实现为准
唯一调度者 runTaskLoop 中的 Orchestrator
外部执行 代码修改落在 worktree + executor
讨论重点 调度链，不讲 Overlay 卡片细节

四条先验约束

  • Orchestrator 是唯一任务生命周期决策者，sub-agent 不直接完成 engine task 的 cancel / fail / retry / propose。
  • Agent 是 agent，Infrastructure 是 infrastructure。skill、plugin、MCP、executor 都不应该被画成"另一个 planner"。
  • 调度分两层：外层是 task control loop，内层是每个 agent / executor session 自己的 tool loop。
  • 执行与回流分离：代码变更、证据、日志先沉到 engine_* / session / trace，再回流给界面和后续决策。

02Agent 全集 · 15 个 native agent

截至 2026-05-21，packages/opencorvus/src/agent/agent.ts 注册 15 个 native agent， agent/role-contract.ts 给出官方一句话职责。下图按"在 task workflow 中的位置"分组： control 与 orchestrator 是控制平面；中间 8 个由 Orchestrator 通过 orchestrator/tools.ts 的显式 dispatch tool 调用；顶 / 底两条带是不在 task 调度链中的 agent。

控制平面 / 分析 (control, intent-analysis, requirements, frontend-design, architect)
编排者 (orchestrator)
read-only / 验收 (explore, integrity, prosecutor)
执行 + 外部执行后端 (build, External Executors)
不入 task workflow 调度链 (coding, general, compaction, title, summary)
orchestrator 显式 dispatch
cross-process 启动 (build → executor)
verdict 回流 (integrity → orchestrator)
counterexample 回流 (prosecutor → orchestrator)

典型调度链路（皆由 orchestrator 选择，非硬编码）

  1. Direct build（task.kind = "build" / 单文件改动）：control → orchestrator → build → External Executor。不展开 requirements / architect / integrity。
  2. Standard pipeline（多文件 / 跨模块）：control → orchestrator → intent-analysis → requirements → architect → per-goal build → External Executor → integrity → verdict 回流 → orchestrator 决策（modify_goal / build / architect / deliver / fail_task）。
  3. Visual / reference pipeline（UI 复刻 / 视觉参考）：control → orchestrator → frontend-design（独占网页证据）→ intent-analysis → requirements → architect → per-goal build → integrity → 回流。
  4. Adversarial review（怀疑 verdict 不够严）：在 integrity pass 之后，orchestrator → prosecutor，产出 counterexample 触发再次 build / architect。
  5. Investigation（任意时刻需要事实）：orchestrator → explore（read-only），结果回填 decision_log，不进入实施链。

04Skill / MCP / Plugin / Executor 基建接入层

这一层最容易被画乱。正确画法是按"接入位置"分层，不按"看起来都能扩展系统"混成一团。

05职责矩阵

对象 接入位置 能影响什么 不能替代什么
Orchestrator orchestrator/loop.ts + orchestrator/tools.ts 任务生命周期、stage 调度、build / deliver / retry 决策 不能把生命周期权力交给 acceptance、plugin、MCP 或 skill
Sub-agent requirements/ · architect/ · integrity/ 等 需求、契约、质检、最终 gate、专项分析 不能单独完成 engine task 调度闭环
Skill agent 显式调用 skill 工具 agent 行为规则、可见工作流说明 不能直接执行工具，也不能决定下一阶段
MCP tool surface / prompt / resource surface 给 agent 增加外部工具、资源、提示词 不能成为新的 Orchestrator
Plugin 全局 runtime hooks 改认证、改参数、插入评估、订阅事件、加工具 不能替代 executor，也不该替代 task loop
Executor build 阶段外部执行后端 在 worktree 里真实写代码、跑命令、产出 diff 不能负责任务规划和全局重试策略
ACP / Channel / Control 入站协议层 把外部请求引到 EngineService 不能替代内层 build loop
