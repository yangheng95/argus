## 1. 执行摘要

OpenCorvus 的业务价值不是“生成更多代码”，而是让真实业务任务通过可恢复的 Agent Team 编排，以更高成功率、更短周期、更少人工返工完成可验证交付。

北极星指标定义为：

> **有效交付任务数**：已合并或上线、业务负责人验收通过、OpenCorvus 自动验收通过，并且 14 天内没有回滚或严重缺陷的唯一真实任务数。

阶段策略：

1. **1 个月：可测量。** 跑通数据链路、建立人工/直接 Agent 对照基线，完成两个灯塔场景。
2. **3 个月：可证明。** 证明 OpenCorvus 相比直接 Agent 在成功率、周期或成本上形成稳定改善，并完成跨团队复用。
3. **6 个月：可规模。** 形成五个业务方向、生产级 Agent Team 资产供给、长程 Mission 与可信 Benchmark 的运营闭环。

## 3. 1/3/6 个月推进安排

### 3.1 第 1 个月：可测量与灯塔闭环

**阶段目标：** 所有核心指标能够由真实任务证据计算，两个高频业务方向形成从提交到上线/验收的完整闭环。

关键工作：

1. 确定任务唯一性、业务方向、复杂度分层、上线/合并、缺陷等级和人工干预事件定义。
2. 打通 `engine_task`、Session cost/token、criteria results、Decision Log 与外部上线/缺陷记录的关联。
3. 选择两个灯塔方向，每个方向至少完成 10 个真实任务。
4. 建立三组对照：人工流程、直接 Coding Agent、OpenCorvus。
5. 建立 100 个分层 Case 和 LLM-as-Judge 人工校准集。
6. 对现有 Expert Squad、Skill、MCP 和通道做生产级认证，不把“目录存在”计为可用。

月末通过条件：

- ≥20 个有效交付任务且有效交付率 ≥65%。
- 核心指标数据完整率 ≥95%，每条结果可回溯到 Task、Evidence 和验收人。
- 两个灯塔方向均产生复用，至少一个长程 Mission 完成故障恢复演练。
- 输出基线报告；不要求第一个月宣称效率提升。

### 3.2 第 3 个月：证明业务改善与跨团队复用

**阶段目标：** 在至少三个业务方向证明 OpenCorvus 相比直接 Agent 有可重复的质量或效率优势。

关键工作：

1. 把灯塔模式复制到第三个业务方向，累计 ≥85 个有效交付。
2. 上架 6 个生产级业务 Expert Squad 和 8 个通用 Skill/MCP。
3. 建立跨专家团 Mission 模板，累计完成 ≥30 个长程 Mission。
4. Benchmark 扩展到 300 Case、10 个环境、8 万有效轨迹。
5. 完成 LLM-as-Judge 校准，使人工一致率 ≥85%、误通过率 ≤5%。
6. 发布按业务方向、任务类型、模型、Expert Squad、成本与失败根因切片的月报。

季末通过条件：

- 有效交付率 ≥72%，首轮通过率 ≥58%，缺陷逃逸率 ≤5%。
- 同类任务交付周期中位数改善 ≥20%，或在周期持平时单个有效交付成本下降 ≥15%。
- OpenCorvus 相对直接 Agent 的 Benchmark 解决率提升 ≥10 个百分点。
- 30 天复用率 ≥45%，不存在只靠单一团队贡献全部增长的情况。

### 3.3 第 6 个月：规模化供给与运营闭环

**阶段目标：** 形成五个业务方向、双通道 Expert Squad 供给、长程 Mission 和 Benchmark 驱动迭代的规模化平台。

关键工作：

1. 扩展到五个活跃业务方向，累计 ≥280 个有效交付。
2. 形成 12 个生产级业务 Expert Squad，其中 ≥65% 通过轻量导入路径形成。
3. 累计完成 ≥120 个长程 Mission，并将 Checkpoint 恢复成功率提升到 ≥98%。
4. Benchmark 扩展到 600 Case、15 个环境和 25 万有效轨迹，真实内部任务占比 ≥70%。
5. 建立月度资产淘汰机制：低复用、低成功率或证据不完整的资产下架整改。
6. 形成可审计的经营看板，将业务采用、交付质量、效率、成本和平台可靠性放在同一视图。

六月末通过条件：

- 有效交付率 ≥80%，首轮通过率 ≥68%，14 天缺陷逃逸率 ≤3%。
- 交付周期中位数改善 ≥30%，单个有效交付成本改善 ≥25%。
- 相对直接 Agent 的 Benchmark 解决率提升 ≥15 个百分点。
- 30 天复用率 ≥55%，服务可用性 ≥99.9%，Evidence 完整率 100%。

## 4. 口径与数据治理

### 4.1 禁止作为一级 KPI 的指标

- **代码行数：** 与业务价值、质量和可维护性没有稳定正相关关系。
- **PRD/设计稿数量：** 仅能证明产生文档，不能证明完成交付。
- **Skill/MCP 目录数量：** 只有经过真实任务复用与验证的资产才计入生产级供给。
- **原始 Session 数：** 空跑、重试和启动失败会虚增，必须使用“有效评测轨迹”。
- **单一 Benchmark 总分：** 必须同时报告真实任务占比、误通过率、成本和重复运行波动。

### 4.2 数据单一来源

| 数据 | 单一来源 | 第 1 月需补齐 |
| --- | --- | --- |
| 任务量、起止时间、终态 | `engine_task` 与派生状态 | 业务方向、任务类型、复杂度标签 |
| 验收与 Evidence | `criteria_results`、metric result、artifact | 上线/合并引用与业务验收人 |
| 成本与 Token | Session assistant usage | 按 Task 聚合的统一查询 |
| 人工干预 | interaction、control、Decision Log | 区分权限确认与纠错/接管 |
| 缺陷逃逸 | 缺陷/回滚系统 | Task 到缺陷记录的关联标识 |
| 复用率 | 真实使用者与团队标识 | 合规的匿名使用者 ID |
| 对照基线 | Benchmark experiment | 同 Case、同模型、同预算实验协议 |

### 4.3 指标审计规则

1. 数量类指标累计统计，比例类指标采用检查点前 30 天滚动窗口。
2. 任务拆分不能增加业务价值计数：同一验收目标的子任务按一个业务任务统计。
3. 失败、取消和阻塞任务必须保留在分母中，禁止通过删除记录改善成功率。
4. 无新鲜 Evidence 的结果不计入通过；现有 metrics schema 已有 `evidence_fresh` 支持这一约束。
5. 所有 A/B 对照固定 Case、模型、预算、环境和验收器，仅改变是否使用 OpenCorvus Harness。
6. 每月人工抽检不少于 10% 的有效交付和 10% 的自动失败样本。

## 5. 经营看板与责任机制

### 5.1 看板分层

- **管理层：** 有效交付、交付率、周期改善、缺陷逃逸、复用率、成本改善。
- **业务负责人：** 本方向任务漏斗、未通过原因、收益案例、待沉淀资产。
- **平台团队：** 可用性、恢复率、Evidence 完整率、通道覆盖、成本与延迟。
- **Benchmark 团队：** Case 结构、解决率提升、误通过、Judge 一致率、波动和污染检查。

### 5.2 评审节奏

- 每周：检查数据完整性、失败根因和灯塔任务推进。
- 每月：复核北极星指标、质量护栏和资产生产级认证。
- 第 1/3/6 个月：按本文阶段通过条件进行里程碑评审。
- 未达到护栏时不得用任务量或 Session 量替代；必须列出未达成项、证据和根因。

## 6. 风险与应对

| 风险 | 识别信号 | 应对 |
| --- | --- | --- |
| 为冲数量拆分任务 | 任务数上涨但业务验收目标不变 | 按唯一业务验收目标去重 |
| Benchmark 过拟合 | 公开 Case 上升、内部真实任务不升 | 保持内部真实任务占比并滚动加入新 Case |
| LLM Judge 误通过 | 自动通过、人工复核失败 | 双人标注校准，持续监控误通过率 |
| 资产数量虚高 | Skill 多但无人复用 | 生产级认证与月度淘汰 |
| 效率收益被高估 | 自评变快但真实周期未下降 | 使用任务时间戳与对照实验，不用主观估计 |
| 平台规模先于可靠性 | Session 增长但失败/恢复恶化 | 有效轨迹与可用性、恢复率绑定汇报 |
