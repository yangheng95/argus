# Route design production contract

Require one PRD, its same-route screenshots/assets, output path and shared-system interfaces. Declare
`DESIGN_INTENT` with hierarchy, density, interaction and design-authority decisions before editing.

First build a product-capability inventory and classified evidence map. Reference observations
constrain product structure, data, behavior, journeys, states and accessibility. Competitor material
contributes only explicit adopt, defer or reject decisions. The designer must author original layout,
geometry, hierarchy, regions and component composition while resolving styling exclusively from the
mapper's cited AInvest identity, semantic tokens, components, assets, interactions, market colors,
compliance and light/dark authority. Materialize only approved AInvest assets locally.

Run two explicit passes:

1. skeleton pass establishing document structure, ordered regions, layout, data placeholders and
   state containers;
2. full pass implementing components, content/data examples, interactions, all required states,
   keyboard/focus behavior, accessibility and reduced motion.

Produce one self-contained route design under the exact task-scoped `visual-html-skeleton` root
supplied by the Frontend Design dispatch packet, using repository-approved tooling and the cited
AInvest design authority. Launch it through `capture_frontend_visual_evidence` with `kind: "render_review"`,
capture canonical task-scoped screenshots, exercise material interactions, inspect diagnostics, review
the current original hierarchy/module order/density/spacing and correct discrepancies. Persist output
path/digest, asset list, states
exercised, screenshots, diagnostics, known limitations and shared-interface needs through the typed
Frontend Design Artifact. Downstream consumers discover and exactly read it from the Task Catalog;
the visible final message is natural narration. A partial or inconsistent Frontend Design fact or
capture is a blocker, not a completed route design.
