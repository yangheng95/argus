## Parallel Execution & Isolation

Goals are executed **in parallel, each in an isolated git worktree**. Maximize parallelism:

- **Parallel-first design**: The default state is that goals have NO dependencies and run simultaneously. Only add `depends_on_goal_ids` when there is a genuine data dependency (one goal MUST read output produced by another). Do NOT add dependencies just because goals touch the same domain — if their interfaces are well-defined, they can run in parallel.
- **File ownership must be disjoint**: Two concurrent goals MUST NOT write to the same file. If two goals both need to modify `src/index.ts`, one must depend on the other OR a final integration goal should wire them together.
- **Shared code goes into a bootstrap goal**: Types, interfaces, config schemas, database migrations, and any code needed by multiple goals MUST be in an early bootstrap/infrastructure goal that others depend on. This goal runs first and its output is available to all downstream goals. Keep bootstrap goals minimal — only truly shared definitions.
- **Dependencies encode data flow, not domain proximity**: If Goal B reads files produced by Goal A, Goal B MUST list Goal A in `depends_on_goal_ids`. But if Goal A and Goal B work on independent modules that will be integrated later, they SHOULD NOT depend on each other — use an integration goal instead.
- **Minimize cross-goal coupling**: Design goals so each one produces a self-contained module. Avoid designs where many goals modify a single shared entry point file — instead, use a final integration goal that wires modules together.
- **Owned paths = exclusive write access**: During execution, each goal can ONLY write to its `owned_paths`. If you assign `src/db.ts` to Goal A, no other concurrent goal may modify it.
- **Anti-pattern: serial chain**: If your goals form a strict linear chain (A→B→C→D→E), your decomposition has failed. A well-decomposed plan should have most feature goals at the same dependency depth, branching from a shared bootstrap.

CREATE TABLE users (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  username TEXT NOT NULL UNIQUE,
  password_hash TEXT NOT NULL,
  balance REAL NOT NULL DEFAULT 1000000,
  created_at INTEGER NOT NULL DEFAULT (unixepoch())
);

CREATE TABLE sessions (
  token TEXT PRIMARY KEY,
  user_id INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  created_at INTEGER NOT NULL DEFAULT (unixepoch())
);

CREATE TABLE stocks (
  code TEXT PRIMARY KEY,
  name TEXT NOT NULL,
  open_price REAL NOT NULL,
  current_price REAL NOT NULL,
  high_price REAL NOT NULL,
  low_price REAL NOT NULL,
  volume INTEGER NOT NULL DEFAULT 0,
  trend REAL NOT NULL DEFAULT 0,
  updated_at INTEGER NOT NULL DEFAULT (unixepoch())
);

CREATE TABLE price_history (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  stock_code TEXT NOT NULL REFERENCES stocks(code),
  price REAL NOT NULL,
  volume INTEGER NOT NULL DEFAULT 0,
  created_at INTEGER NOT NULL DEFAULT (unixepoch())
);

CREATE TABLE orders (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  user_id INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  stock_code TEXT NOT NULL REFERENCES stocks(code),
  direction TEXT NOT NULL CHECK(direction IN ('buy', 'sell')),
  quantity INTEGER NOT NULL,
  price REAL NOT NULL,
  status TEXT NOT NULL DEFAULT 'pending' CHECK(status IN ('pending', 'filled', 'cancelled')),
  filled_at INTEGER,
  created_at INTEGER NOT NULL DEFAULT (unixepoch())
);

CREATE TABLE positions (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  user_id INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  stock_code TEXT NOT NULL REFERENCES stocks(code),
  quantity INTEGER NOT NULL DEFAULT 0,
  cost_basis REAL NOT NULL DEFAULT 0,
  UNIQUE(user_id, stock_code)
);

CREATE TABLE daily_snapshots (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  user_id INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  total_assets REAL NOT NULL,
  created_at INTEGER NOT NULL DEFAULT (unixepoch())
);
