## 帮我启动下面的长程 Mission：完整加密货币交易系统（任务C）

请创建并执行一个长程 Mission，目标是从 0 到 1 设计并实现一个完整的加密货币交易系统。这个 Mission 必须先做竞品分析和产品调研，再进行系统设计，最后逐层逐级实现前端、后端、数据库、行情模拟、交易模拟、页面交互和测试验收。

### 总目标

实现一个可本地运行的加密货币交易系统 Demo，但不能做成静态页面、占位 UI 或假组件拼图。系统必须包含真实业务链路：

- 前端交易终端：市场列表、行情概览、交易对详情、K 线图、技术指标、订单簿、逐笔成交、下单面板、资产与持仓、委托记录、成交记录、收藏/自选、告警或模拟风控提示。
- 后端服务：市场数据 API、交易对/资产 API、账户与资产 API、订单 API、成交 API、行情 WebSocket 或等价实时推送、模拟撮合/成交逻辑、行情模拟引擎、测试/诊断接口。
- 数据层：使用真实数据库 schema 和迁移/初始化脚本，存储交易对、OHLCV K 线、tick、order book snapshot、trades、accounts、balances、orders、fills、positions、watchlists、alerts、audit logs 等业务数据。
- 行情数据：使用真实合成数据，不允许写死几条数组冒充行情。必须构建行情生成器和可重复 seed，生成多交易对、多周期、多行情状态的数据，例如趋势、震荡、插针、放量、跳空、极端波动和低流动性。
- 交易模拟：不接真实交易所、不发真实订单。用本地模拟撮合和账户资金模型实现限价单/市价单/撤单/部分成交/手续费/滑点/余额冻结/成交回报。

### 第一阶段：竞品分析与产品调研

先调研加密货币交易和行情产品的竞品，至少覆盖：

- 中心化交易所终端：Binance、OKX、Bybit、Coinbase Advanced、Kraken Pro 等。
- 行情/图表工具：TradingView、CoinMarketCap、CoinGecko、Dexscreener、GeckoTerminal 等。
- 专业交易体验：订单簿深度、K 线指标、盘口、成交明细、资产/委托/成交联动、快捷下单、风险提示、实时状态反馈。

调研交付物必须包含：

- 竞品信息架构对比。
- 页面与组件清单。
- 关键交互模式。
- 行情/交易数据模型归纳。
- 本系统采用和舍弃的功能范围。
- 不得直接复制品牌视觉、图标、文案或受版权保护素材；只吸收信息架构、交互语义和业务组件模式。

### 第二阶段：产品与技术设计

基于调研结果输出系统设计方案，并把实现拆成可执行的递进任务。设计必须包括：

- 页面地图和路由结构。
- 后端模块边界。
- 数据库 schema。
- API 和实时推送事件契约。
- 行情模拟引擎设计。
- 模拟撮合和账户资产设计。
- 前端状态管理和数据订阅方案。
- 测试策略、验收指标和风险清单。

必须明确每个页面依赖哪些 API、哪些 WebSocket 事件、哪些数据库表和哪些业务组件。

### 第三阶段：后端与数据基础实现

优先实现后端和数据层，确保前端不是无源 UI。要求：

- 建立数据库 schema、初始化脚本和 seed 数据。
- 实现行情生成器，支持生成 BTC/USDT、ETH/USDT、SOL/USDT、BNB/USDT、XRP/USDT 等多个交易对的 OHLCV、tick、order book 和 trade 流。
- 实现市场数据查询 API：交易对列表、行情概览、K 线历史、盘口、逐笔成交、涨跌幅、成交量、24h 统计。
- 实现实时行情推送：K 线增量、盘口增量、逐笔成交、ticker 更新。
- 实现账户与交易 API：余额、持仓、委托、成交、下单、撤单。
- 实现模拟撮合：限价单、市价单、部分成交、手续费、余额冻结、成交回报、订单状态流转。
- 所有 API 必须有 schema 校验和错误响应，不允许 silently fallback。

### 第四阶段：前端逐层逐级实现

逐页实现前端，每个页面和核心业务区域都要拆成独立 goal。禁止手搓占位组件，必须使用成熟业务组件或成熟可验证库：

- K 线图必须使用成熟图表库，例如 TradingView Lightweight Charts、Apache ECharts candlestick，或同等级金融图表库；必须支持 OHLCV、十字光标、缩放、周期切换、成交量和指标 overlay。
- 技术指标至少实现 MA、EMA、MACD、RSI、Bollinger Bands 中的多项，指标计算必须来自明确的计算模块或成熟库，不允许只画静态线。
- 订单簿、深度图、逐笔成交、行情表格、下单表单、资产表格、委托表格必须绑定真实 API/mock 数据流。
- 所有加载、空状态、错误状态、断线重连、行情暂停/恢复、下单成功/失败、余额不足、订单部分成交等状态必须有真实 UI。
- 页面必须包括：市场首页、交易终端页、交易对详情页、资产/持仓页、委托与成交历史页、自选/告警页、系统诊断或模拟器控制页。
- 前端设计应体现专业交易产品的信息密度和可扫描性，避免营销落地页风格。

### 第五阶段：系统联调与 OpenTest 验收

使用 OpenTest 专家团队测试完整系统，测试范围包括：

- 功能测试：行情展示、周期切换、指标计算、盘口更新、下单、撤单、部分成交、余额冻结、委托/成交联动、页面跳转、筛选排序、自选和告警。
- 性能测试：大量 tick 推送、K 线滚动、盘口更新、表格刷新、WebSocket 长连接、前端渲染性能。
- 安全测试：输入校验、订单参数边界、越权访问模拟、防止负余额/超额下单、错误信息泄露、API schema 强校验。
- 数据一致性测试：订单状态、成交记录、余额冻结释放、手续费、持仓变化、行情时间序列连续性。
- 视觉与交互测试：真实浏览器截图检查，重点检查交易终端布局密度、K 线可读性、盘口/成交/下单面板联动、移动端如未授权则不作为交付范围。

验收报告必须列出：

- 已实现页面和业务链路。
- 数据库和行情模拟说明。
- API/实时事件清单。
- 使用的成熟业务组件/库及其用途。
- 测试用例、测试结果、失败项和修复记录。
- 未完成项必须明确标记为未达成，不能写成“基本完成”。

### 硬性约束

- 禁止占位页面、占位卡片、静态假图、写死行情数组、假按钮、伪下单、伪实时。
- 禁止手搓 K 线图、技术指标、复杂表格或交易业务组件；能用成熟库就必须用成熟库。
- 禁止接入真实交易所下单或真实账户；所有交易必须是本地模拟。
- 禁止用 fallback/兜底逻辑掩盖数据、API、撮合或图表问题。
- 不达到验收指标就继续修复、复测和重新截图。
