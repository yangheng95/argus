  分析报告：Overlay 角色卡片与通信协议                                                                            
                                                                                                                    一、角色卡片显示协议分析                                                                                                                                                                                                            1.1 当前的角色分类体系                                                                                                                                                                                                              系统有两套独立的角色分类逻辑，存在架构性冲突：                                                                                                                                                                                      ┌─────────────────┬───────────────────────────────────┬──────────────────────────────────────┬─────────────┐      │    分类系统     │               位置                │               分类依据               │    产出     │    
  ├─────────────────┼───────────────────────────────────┼──────────────────────────────────────┼─────────────┤
  │ AgentCard 分类  │ messages.ts:279                   │ msg.info.agent 是否属于 AGENT_STAGES │ 5           │    
  │                 │ classifyAgentStage()              │                                      │ 个卡片阶段  │    
  ├─────────────────┼───────────────────────────────────┼──────────────────────────────────────┼─────────────┤    
  │ MessageView     │ message.ts:164 effectiveRole()    │ agent name + sessionID + source      │ 9 个角色    │    
  │ 角色            │                                   │ 综合判断                             │             │    
  └─────────────────┴───────────────────────────────────┴──────────────────────────────────────┴─────────────┘    

  AGENT_STAGES 只认 5 个硬编码值：spec, planner, goal, judge, delivery

  问题 1：executor 不是 AGENT_STAGE

  classifyAgentStage() 中 executor 不在 AGENT_STAGES 里，所以 executor 的消息永远不会被归入 AgentCard。executor   
  走的是完全独立的 buildExecutorMessages() 路径，产出 ExecutorGoalBlock 组件。

  但 effectiveRole() 里，executor 的识别逻辑极其复杂（message.ts:164-203）：

  // 1. 不是 user → 检查 sessionID 是否是 child session
  // 2. 如果 goalSessionIDs 有且匹配 → "executor"
  // 3. 否则取 agent name → agentStageRole() 映射
  // 4. agentStageRole 把 "executor"/"build"/"coding" 映射到 "assistant" → 再硬改成 "executor"

  这是一个三层间接映射（agent name → stageRole → 再 remap），容易导致边缘情况下 executor 消息被错误识别。

  问题 2：classifyAgentStage vs classifyMessage 逻辑重复但不一致

  - messages.ts:279 classifyAgentStage() —— 用于 AgentCard 构建
  - conversation.ts:38 classifyMessage() —— 用于 conversationMessages 过滤

  两者都做 agent name → channel 分类，但有微妙差异：
  - classifyAgentStage 把 user role 的 agent stage 消息归入 "main"
  - classifyMessage 也这么做，但还额外处理 agent === "agent" 的 legacy case

  这意味着同一条消息可能在两个系统里被不同分类。

  问题 3：调度器 (scheduler/judge/evaluator) 名称混乱

  后端用的名称不统一，overlay 用字符串 includes() 做模糊匹配：

  // phaseFromAgent — 模糊匹配
  text.includes("scheduler") || text.includes("evaluator") ||
  text.includes("evaluation") || text.includes("evaluate") || text.includes("review")

  // agentStageRole — 精确匹配
  "judge" || "evaluation" || "scheduler" → "scheduler"

  // AGENT_STAGES — 只认 "judge"

  这意味着：
  - 后端发 agent: "evaluator" → AGENT_STAGES 不认（只认 "judge"）→ 不会创建 AgentCard
  - 后端发 agent: "scheduler" → AGENT_STAGES 不认 → 不会创建 AgentCard
  - phaseFromAgent 能认出来但仅用于 board context messages

  这是执行器跟调度器卡片合并问题的根因之一。

  问题 4：goal stage 有 AgentCard 但 goal agent 发出的消息 agent 名可能不是 "goal"

  后端 GoalAgent 在 goal/agent.ts 定义，但它的消息的 agent 字段实际值取决于 session 配置，可能是 "goal"
  也可能是其他值。如果不是精确的 "goal" 字符串，就不会被 AGENT_STAGES 匹配到。

  1.2 卡片与消息的多路合并问题

  conversationMessages() 在 conversation.ts:295 做了 4 路合并：

  const result = [...filteredMain, ...executorMsgs, ...boardMsgs, ...agentCardMsgs]
    .sort((a, b) => (a.info?.time?.created || 0) - (b.info?.time?.created || 0));

  问题：
  - 时间排序可能把不同来源的消息交叉排列
  - Board context 的 synthetic 消息时间戳是手动构造的（如 task.time.created - 2），与真实消息时间戳混排
  - 执行器消息和 AgentCard 消息可能覆盖相同的内容，导致重复显示

  1.3 结论：角色卡片协议不合理不完备

  核心缺陷：
  1. 没有统一的 Agent Identity 枚举——后端有 15+ 个 agent 名，前端用 5 个硬编码字符串 + 多处模糊匹配
  2. 两套并行分类系统（AgentCard vs effectiveRole）语义重叠但不一致
  3. executor 被完全排除在 AgentCard 体系之外，走独立路径，导致架构割裂
  4. evaluator/scheduler/judge 命名不统一，AGENT_STAGES 只认 "judge"，其他名称变体被漏掉

  二、通信协议分析（ACP → Overlay）

  2.1 执行器事件链路

  Executor (codex/claude-code)
    → ACP session events (tool_call, tool_result, text_delta, reasoning_delta)
    → consumeExecutorEvents() [executor-session.ts]
    → Bus.publish(Event.RunProgress / Event.RunOutput)
    → ProtocolStore.appendEvent()
    → SSE: /task/:taskID/events
    → Overlay: routeSSEEvent() → appendExecutorEvent()
    → executorStore.events
    → buildExecutorProcesses() → buildExecutorMessages()
    → ExecutorGoalBlock 渲染

  2.2 执行器细节暴露程度

  当前 ExecutorGoalBlock (ExecutorGoalBlock.tsx) 的渲染能力极其有限：

  // 每个 process 只显示：
  <span class="executor-tool-icon">{displayToolIcon(proc().toolName)}</span>
  <span class="executor-tool-name">{proc().toolName || proc().title}</span>
  <span class="executor-tool-detail">{proc().toolDetail}</span>
  <pre class="executor-tool-output">{output()}</pre>  // 最多 6 行

  具体缺陷：

  ┌─────────────────────────────────┬─────────────────────────────────────┬────────────────────┐
  │          原生 CLI 显示          │            Overlay 显示             │        差距        │
  ├─────────────────────────────────┼─────────────────────────────────────┼────────────────────┤
  │ 完整的 Edit diff（old → new）   │ 只有 tool name "edit" + file path   │ 看不到代码改了什么 │
  ├─────────────────────────────────┼─────────────────────────────────────┼────────────────────┤
  │ Bash 命令 + 完整输出            │ tool name "bash" + 最多 6 行 output │ 严重截断           │
  ├─────────────────────────────────┼─────────────────────────────────────┼────────────────────┤
  │ Read 文件内容                   │ tool name "read" + file path        │ 完全不显示读了什么 │
  ├─────────────────────────────────┼─────────────────────────────────────┼────────────────────┤
  │ Write 完整文件内容              │ tool name "write" + file path       │ 完全不显示写了什么 │
  ├─────────────────────────────────┼─────────────────────────────────────┼────────────────────┤
  │ Reasoning/thinking 完整流式显示 │ reasoning_delta 事件存在但...       │ 见下文             │
  ├─────────────────────────────────┼─────────────────────────────────────┼────────────────────┤
  │ 代码块高亮                      │ <pre> 纯文本                        │ 无语法高亮         │
  └─────────────────────────────────┴─────────────────────────────────────┴────────────────────┘

  2.3 ACP 协议本身是否完备

  从后端 acp/agent.ts 的 event handler 看，ACP 协议本身是有能力传输完整信息的：

  // Tool call: 包含完整 input（命令、文件路径、代码内容）
  case "running":
    connection.sessionUpdate({ type: "tool_call_update",
      toolCall: { id, kind, name, input, status: "in_progress", locations } })

  // Tool result: 包含完整 output
  case "completed":
    connection.sessionUpdate({ type: "tool_call_update",
      toolCall: { id, kind, name, input, status: "completed",
        content: [{ type: "text", text: output }] } })

  // Edit 工具特殊处理：传输 diff
  if (name === "edit") {
    content.push({ type: "diff", oldText, newText, filePath })
  }

  但问题在于：Overlay 不是 ACP client。 Overlay 通过 SSE 接收的是 ProtocolStore 持久化后的 run.progress
  事件，这些事件经过了 consumeExecutorEvents() 的简化转换：

  // executor-session.ts — 事件被简化
  Bus.publish(Event.RunProgress, {
    type: event.type,
    summary: event.summary ?? event.type,  // 只有 summary
    payload: event.payload,                // payload 结构不确定
  })

  event.payload 的结构取决于底层执行引擎（codex vs claude-code vs 其他），没有统一 schema。Overlay 端的
  executorTargetText() 尝试从 payload
  中提取显示文本，但它的逻辑是启发式的——检查各种可能的字段名，没有可靠的协议保证。

  2.4 Thinking/Reasoning 导致乱码问题

  reasoning_delta 事件在 overlay 中走两条路径：

  1. AgentCard 路径（agentMessage() in messages.ts:406）：
  if (kind === "reasoning_delta" && text) {
    parts: [{ type: "reasoning", text }]
  }
  2. Executor 路径（executorMessage() in executor-events.ts:552）：
  type: event.kind === "reasoning_delta" ? "reasoning" : "text"

  问题：
  - reasoning_delta 是增量事件（每次只有几个 token），但被当成独立消息渲染
  - 多个 reasoning_delta 不会合并——每个 delta 生成一个独立的 part/message
  - 如果模型开启 extended thinking，会产生大量碎片化的 reasoning 消息，视觉上就是"乱码"
  - _targetText 和 _liveText 用于文字动画，但合并逻辑在 executor store 的 mergeExecutorEventsFromFetch 中只处理了 
  message_delta，reasoning_delta 的合并逻辑不完整

  2.5 结论：通信协议不完备

  核心缺陷：
  1. Executor 事件没有统一 schema——payload 结构取决于底层引擎，overlay 用启发式解析
  2. ACP 传输了完整信息（diff、完整 output）但 overlay 不是 ACP client，收不到这些信息
  3. 工具调用细节严重丢失——edit diff、bash 完整输出、read 内容在 overlay 不可见
  4. reasoning_delta 没有合并机制——增量 token 被当独立消息渲染，造成乱码
  5. 没有 code block 渲染——所有文本都是 <pre> 纯文本，无语法高亮

  四、修复方向建议

  1. 统一 Agent Identity：建立一个后端-前端共享的 AgentRole 枚举，消除字符串模糊匹配
  2. 让 Overlay 成为 ACP-aware：将 ACP 的 tool_call_update（含 diff、完整 output）直接推送到 overlay，而不是经过  
  ProtocolStore 的简化
  3. executor 纳入 AgentCard 体系：或者至少让 ExecutorGoalBlock 具备与 ToolPart 同等的渲染能力（显示
  diff、完整命令输出）
  4. reasoning_delta 合并：在 executor store 层面合并连续的 reasoning delta，而不是生成独立消息
  5. 代码渲染能力：添加 code block 语法高亮，diff 视图渲染
