# 定位

我要一个独立于coding assistant的工具，他被用来解决自动化开发的问题。传统的coding开发需要开发者自己来或者在线使用coding agent，无法托管开发任务。导致开发效率特别低。因此我想开发一个工具，opencorvus，它能够在开发者和coding工具之间搭建一个桥梁。
简而言之，开发者发布任务，opencorvus接受任务，然后调度coding工具开发，支持内置执行器、codex、claude code等工具。

# 实现方式

1. opencorvus主体是一个聊天接口，用户通过这个接口发布开发任务，opencorvus会解析任务内容，先调用一等 `spec agent` 研究、澄清并编写/补完 spec，再基于 spec 生成开发计划，并调度相应的coding工具进行开发。`spec` 不再作为 builtin skill，而是与 `plan` 类似的独立 agent。
2. opencorvus监听用户的反馈和追加需求，偏好，能够动态调整开发计划和任务分配，确保开发过程的灵活性和高效性。偏好和记忆同时支持会话级与长期全局级，默认写入长期全局，必要时才写入会话级。
3. opencorvus同时监听coding工具的开发进度和结果，能够及时反馈给用户，并根据开发结果调整后续的开发计划和任务分配。具体支持能力取决于coding工具的接口和功能，但总体目标是实现一个高效的开发流程管理系统。
4. opencorvus具有 spec 编写/补完、任务分解，目标制定，进度跟踪，结果评估和最终交付等工具/功能，能够帮助开发者更好地管理和执行开发任务，提高开发效率和质量。
5. 制定目标： opencorvus能够根据用户的需求和任务内容，先形成准确、可执行的 spec，再从 spec 中提炼明确的开发目标、里程碑和验收标准，确保开发过程的有序进行和结果的可衡量性。
6. 任务分解： opencorvus能够将复杂的开发任务分解成更小的子任务，但分解动作必须建立在已编写完成的 spec 之上。待机等待用户发布任务和随时更新需求，及时调整 spec 与开发计划。
7. 进度跟踪： opencorvus能够实时跟踪开发任务的进度，及时反馈给用户，并根据开发进度调整后续的开发计划和任务分配。取决于coding工具的接口和功能，但总体目标是实现一个高效的开发流程管理系统。
8. 结果评估： opencorvus能够根据开发结果进行评估，支持可插拔扩展评估工具，例如代码语法检查，CR评审工具，视觉评估工具（网页）等，帮助开发者更好地评估开发结果的质量和符合度。调度过程中的 `LLM judge` 调整为 `spec check`，并默认勾选；只有 required spec 全部被准确、完备地实现时，任务才可验收通过。评估结果不符合 spec 或目标则重新编写 spec、任务分解和开发计划调整。
9. 最终交付： opencorvus当前已经实现独立的delivery阶段。系统可以生成工作区patch与变更文件摘要、session HTML trace，以及git工作区/分支预览，并把交付结果与artifact写入数据库并展示在任务面板中；但只有 `spec check` 确认 required spec 全部完成后，这些delivery产物才会被视为可验收交付。当前交付适配器以 `workspace_export`、`artifact_export`、`git_publish` 为主，发布模式为 manual 预览/导出模式，尚未扩展到真实仓库发布、部署平台发布或完整文档生成流水线；当前delivery失败时任务会直接标记为失败。
10. opencorvus有一个数据库，用于存储用户的开发任务，开发计划，开发结果，评估结果和交付结果等信息，支持数据的查询和分析，帮助开发者更好地管理和优化开发流程。
11. opencorvus具有一个用户界面，用户可以通过这个界面发布开发任务，查看 spec 与开发计划，跟踪开发进度，评估开发结果和完成最终交付等操作。用户界面应该简洁易用，能够提供清晰的反馈和指导，帮助用户更好地管理和执行开发任务。
12. opencorvus支持多种编程语言和开发框架，能够适应不同类型的开发任务和开发者的需求。具体支持的编程语言和开发框架取决于coding工具的接口和功能，但总体目标是实现一个灵活的开发流程管理系统。
13. opencorvus具有能够自由调用上述的主要工具，也能够使用通用工具，例如网页搜索工具，数据库查询工具，文件管理工具等，帮助开发者更好地完成开发任务的各个环节。具体支持的通用工具取决于coding工具的接口和功能，但总体目标是实现一个高效的开发流程管理系统。
14. opencorvus支持内置 skill、tool、agent 等能力，能够更好地利用系统自身能力来完成开发任务。`spec` 应升格为与 `plan` 类似的一等 agent，而不是 builtin skill；对于中大型需求，系统应被鼓励主动调用 `spec agent`，先完成 spec，再进入 plan。具体支持的功能取决于接口和运行能力，但总体目标是实现一个高效的开发流程管理系统。
15. 用户面板的主体仍然是聊天窗口，但当前实现采用“顶部任务/状态工具栏 + 左侧聊天区域 + 右侧折叠信息区”的布局。用户可以在聊天窗口中发布开发任务，在右侧查看 spec、plan、goals、验收项、评估结果和 delivery 信息，并在顶部切换执行器、查看任务状态和管理 task session。其中 `spec` 应位于 `plan` 之前，作为后续规划与验收的基准。
16. opencorvus支持远程自动开发，用户可以通过channel例如slack连接到opencorvus系统，发布开发任务并跟踪开发进度，无论他们身在何处。具体支持的远程自动开发功能取决于coding工具的接口和功能，但总体目标是实现一个灵活的开发流程管理系统。
17. opencorvus支持session管理，新建/删除/切换/导出session，能够帮助用户更好地管理和组织开发任务。每个session可以对应一个独立的开发项目，用户可以在不同的session之间切换，查看和管理不同的开发任务和计划。具体支持的session管理功能取决于coding工具的接口和功能，但总体目标是实现一个高效的开发流程管理系统。
18. opencorvus的面板是非阻塞的，按钮和输入框等交互元素可以随时使用，均是高效实现，用户可以在任何时候发布开发任务，查看开发计划和跟踪开发进度等操作，而不需要等待其他操作完成。用户界面应该简洁易用，能够提供清晰的反馈和指导，帮助用户更好地管理和执行开发任务。
19. opencorvus拥有完善的与coding工具的通信协议，最大程度以原生API的方式调用coding工具的功能，确保开发流程的高效和稳定。对于不支持的API，opencorvus可以通过模拟用户操作或者其他方式来实现与coding工具的交互，确保开发流程的顺利进行。具体支持的通信协议和交互方式取决于coding工具的接口和功能，例如读取文件系统，系统截屏反馈用户等等。
20. opencorvus的session本地与远程同步，用户可以在本地和远程环境中无缝切换（resume），确保开发任务的连续性和灵活性。具体支持的同步功能取决于coding工具的接口和功能，但总体目标是实现一个高效的开发流程管理系统。
21. UI布局：当前桌面端最上面是标题栏与连接状态；主体上方是一行 task/status/engine/session 工具栏；中间主体区域为左右两栏，左侧是聊天窗口，右侧是可折叠的 spec、plan、目标、验收项、评估与交付信息区。`spec` 面板需要加入到控件区中，并排在 `plan` 之前；`spec check` 作为默认勾选的验收控件展示在评估区，用于确认 required spec 是否被准确、完备地实现。session 列表与新建/删除/切换/导出操作目前放在独立的 Sessions 管理弹窗中，而不是常驻左侧栏。整体界面以任务选择、聊天驱动和右侧信息面板为主。

# 官方化 Claude/Codex 接入方案

## Summary

- 一次性切换到两条官方主路径：
  - Claude 使用官方 Claude Agent SDK
  - Codex 使用官方 Codex App Server
- 工具能力统一收敛到一套独立的 OpenCorvus MCP server，不再为
    Claude 和 Codex 分别维护私有 tool bridge。
- 结构化输出只走官方支持面：
  - Codex 使用 turn/start.outputSchema
  - Claude 在官方 SDK 出现 schema 级输出前，不再宣称支持协议
        级 structured output，也不再用于 executor-native spec/
        plan 生成。
- 不保留旧兼容路径，不保留可选协议分支，不保留“假支持”能力声
    明。

  基线依据：

- Claude Agent SDK 官方支持 mcpServers
- Codex 官方支持 MCP 配置与 outputSchema
- 本地生成的 codex app-server schema 显示
    TurnStartParams.outputSchema 存在，但没有通用 function-tools
    注入位

## Key Changes

### 1. 工具面统一为独立 MCP server

- 在 src/mcp 下新增正式 server 实现，并在 src/cli/cmd/mcp.ts 增  
    加 opencorvus mcp serve 子命令。
- v1 只支持 stdio 传输，不做 HTTP/SSE 传输。
- opencorvus mcp serve 命令固定参数：
  - --cwd <workspace>
  - --toolset executor
- 新增一个稳定的“可重入启动命令” helper，返回当前 OpenCorvus 的  
    真实启动 argv，用于 Claude/Codex 以子进程方式拉起 opencorvus
    mcp serve。不要假设系统里总有全局 opencorvus。
- MCP server 暴露的 v1 工具集固定为：
  - shell_command
  - read_file
  - find_files
  - search_code
  - apply_patch
  - fetch_url
  - web_search
  - memory
  - preference
  - task_report
- 不暴露这些工具：
  - edit
  - write
  - panel
  - tui
  - planner
  - schedule
  - analytics
  - task
  - question
- 现有外部 MCP client 能力保留在 OpenCorvus 内部，由新的
    OpenCorvus MCP server 统一代理；Claude/Codex 只连接一个 MCP
    server：OpenCorvus 自己。
- MCP server 内部不复制现有工具实现，统一复用 ToolRegistry 和现  
    有 Tool.Info.execute()，只增加一层 MCP <-> Tool.Context 适
    配。

### 2. Claude 改为官方 SDK + MCP，停用非官方扩展面

- claude-code 只保留 Claude Agent SDK 路径。
- 在 ClaudeAgentExecutor.createSdk() 中明确传入 mcpServers，值
    为一个 stdio server 配置，指向 opencorvus mcp serve --cwd
    <workspace> --toolset executor。
- allowedTools / disallowedTools 继续只控制 Claude 原生内置工
    具，不再承担 OpenCorvus 自定义工具桥的职责。
- 所有工具调用统一来自 MCP，不再通过私有 function-tool 注册。
- Claude 的 executor-native spec/plan 生成功能关闭：
  - planningCapabilities.spec = false
  - planningCapabilities.plan = false
- Claude 保留：
  - coding run
  - resume
  - interrupt
  - approval/input 回调
  - MCP 工具调用
- Claude 暂不提供协议级 structured output；不要再用 prompt 约束  
    JSON 的方式对外宣称“官方支持”。

### 3. Codex 改为官方 App Server + MCP + 官方 outputSchema

- codex 只保留 Codex App Server 路径。
- 启动 codex app-server 时，不写 repo 内 .codex/config.toml，而  
    是通过启动参数注入 MCP 配置。
- 采用 -c 覆盖 mcp_servers.opencorvus.* 配置项，把 OpenCorvus
    MCP server 作为官方 Codex MCP server 接入。
- Codex 的工具能力全部走 MCP，不再尝试通过 app-server 私有字段
    注入通用 function tools。
- Codex 的 executor-native spec/plan 生成继续保留，并统一走官方  
    outputSchema。
- Codex 保留：
  - coding run
  - resume
  - interrupt
  - approval/input 请求
  - reasoning / usage / diff / plan update
  - MCP 工具调用
  - structured output

### 4. 执行器抽象与对外元数据改为真实值

- ManagedCodingExecutor 不再默认把所有 coding provider 都标成支  
    持 spec/plan。
- 为 registerCoding() / managed executor 增加显式 planning
    capability 配置：
  - codex: { spec: true, plan: true }
  - claude-code: { spec: false, plan: false }
- PlanningInput / CodingRunInput 保留 outputSchema，但只由
    codex 消费。
- /executor 返回的 features 改为“原生协议真实能力”，不再把 MCP
    工具错算成 native custom tools。
- /executor.tools 返回“模型最终可见工具集”，但每个工具要在
    metadata.surface 中标明：
  - native
  - mcp
- 这次切换后，默认暴露应为：
  - codex: custom_tools=false, structured_output=true,
        mcp=true
  - claude-code: custom_tools=false, structured_output=false,  
        mcp=true
- 删除旧环境开关和旧实现：
  - OPENCORVUS_EXECUTOR_CODEX_PROTOCOL
  - OPENCORVUS_EXECUTOR_CLAUDE_PROTOCOL
  - 旧 CLI/Responses 兼容分支
  - 对应测试与导出

## Implementation Notes

- MCP server 的 tool call 执行使用“每个 MCP 连接一个内部
    session”的模型：
  - 连接建立时创建稳定 sessionID
  - 每个 tool 调用生成新的 messageID 和 callID
- 工具权限与用户提问统一走 MCP 原生 elicitation，不引入
    request_user_input 私有桥：
  - ctx.ask() 转成固定结构的 MCP elicitation
  - 统一响应 schema：decision = allow_once | always_allow |
        reject
- task_report 继续存在，但作为 OpenCorvus 自有 MCP tool，而不是  
    executor 私有 tool。
- apply_patch 作为唯一主写入工具；不再对外暴露 edit / write，避  
    免重复写入语义。
- Codex 的 MCP 注入是进程级配置，不做 thread 级 undocumented 配  
    置注入。
- OpenCorvus 自身已有 external MCP client 能力，新的 MCP server  
    应直接复用它，把外部 MCP tools 代理成统一工具面，避免 Claude/  
    Codex 各自单独再连一遍外部 MCP。
