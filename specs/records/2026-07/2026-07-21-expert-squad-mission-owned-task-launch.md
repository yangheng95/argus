## Causal Chain

Observable behavior: after an expert squad is chosen and the request is submitted, the center surface changes to Task and the new Task is selected.

Direct trigger: the Composer submit branch calls Overlay `createTask({ promptProfile })`, then executes `resetCenterWorkbenchToPrimaryPanel("task")` and `selectTask(result.taskID, ...)`.

Deep cause: the 2026-07-20 direct-activation design reclassified expert-squad selection as a Task launcher and made the Overlay a Task lifecycle owner. That contradicts the product ownership boundary now confirmed by the user: expert-squad choice is Mission configuration, while Task creation and reconciliation belong to Mission. A second projection omission compounds the issue: `expertSquadCatalogScope()` resolves Task root sessions but ignores an already-selected standalone Mission/Chat session, so a correctly profile-bound Mission is rendered with the project catalog's active value instead of its own effective session value.

Why selector-only or navigation-only changes would not fix it: keeping the panel labelled Mission while still posting `/task` would leave a direct, top-level Task with no Mission provenance or lifecycle owner. The creation route and the selected conversation must both move back to the existing Mission path.

## Codex Review Feedback

The implementation-time second grep found that `project-directory-new-chat-browser.test.ts` also submits a selected Watch squad and asserts direct `/task` ownership. The initial plan named `expert-squad-selector-browser` instead, but that fixture only verifies catalog/selector state and eventually sends ordinary Chat. The corrected browser acceptance set is therefore `composer-mention-browser` plus `project-directory-new-chat-browser`; `expert-squad-selector-browser` remains unchanged except for shared locale text. This revision closes the missed call point before implementation continues.

The first Mission browser run then proved `/mission/wake` and Mission conversation hydration but showed the Composer selector reverting to General. Runtime inspection traced that result to `expertSquadCatalogScope()` ignoring selected standalone sessions. The plan now includes the shared scope resolver and focused Mission/Chat session-scope regressions; treating this as a browser wait would preserve the wrong source and is rejected.

The session-scope correction exposed a second, previously masked transition race in the project-directory browser flow. `ChatComposer` first wrote the chosen Watch ID into the currently selected Chat session snapshot, then `handleComposerModeChange()` synchronously cleared that session and changed the canonical catalog request key to project scope. The selected ID therefore disappeared because it belonged to the old request key; keeping it in a pending signal would create a second active-profile source. The revised design prepares the real project-scoped catalog first, selects the requested manifest ID in that exact snapshot, and only then clears the old source and exposes the Mission launcher. The existing catalog loader remains the single backend source, and one shared request-key builder prevents a parallel key format.
