# M08 · 上下文记忆引擎

**优先级**：P1 · 阶段 1
**依赖**：M01（session.store）· M02（实体解析）
**负责范围**：`context.store` · 上下文注入逻辑

> **阶段 0**：不交付 M08。阶段 0 的 LLM 调用通过全量历史消息传递上下文（受 Token 窗口自然限制），不做主动追踪。
> **阶段 1 必须交付**：`context.store`、`buildSystemPromptAppendix`、`updateFromToolCall`、指代消解支持（`AnalysisContext.tickers` 注入 system prompt）。
> **阶段 1 可推迟**：会话摘要（长会话压缩）、`context.history`（上下文快照与撤销）。

---

## 1. 模块目标

在多轮对话中，用户不必每轮都重复说明"哪只股票"、"什么时间段"。
本模块追踪会话中的当前「分析上下文」，在每次 LLM 调用时自动注入，实现指代消解。

---

## 2. 用户故事

- **US-01**：我先问"帮我看茅台的 ROE 趋势"，下一轮问"它的毛利率呢"，工具自动理解「它 = 茅台 = 600519.SH」。
- **US-02**：我问"用2023年的数据"之后，后续问题默认都使用 2023 年，直到我明确切换时间段。

---

## 3. 功能规格

### 3.1 追踪的上下文变量

```typescript
interface AnalysisContext {
  tickers: string[]                  // 当前讨论的股票代码列表（最多 5 个）
  dateRange?: { start: string; end: string }
  reportPeriod?: string              // 最近使用的财报期，如 '2024-Q3'
  lastQueryType?: 'financial' | 'market'
  lastFields?: string[]              // 上次查询的字段列表
}
```

### 3.2 上下文更新规则

每次工具调用完成后，自动更新 `context.store`：
- `get_financial_report` → 更新 `tickers`、`dateRange`、`lastFields`
- `get_market_data` → 更新 `tickers`、`dateRange`

每次用户消息发送前，`useEntityParser` 先尝试从消息中提取实体更新上下文，
再将上下文拼入 system prompt 末尾：

```
当前分析上下文：
- 当前标的：贵州茅台（600519.SH）
- 时间范围：2021-01-01 ~ 2024-09-30
- 上次查询字段：roe, revenue, net_profit
```

### 3.3 上下文切换条件

| 触发 | 行为 |
|---|---|
| 用户提及新的公司名 | `tickers` 替换为新标的（不累加，除非用「还有」「以及」等并列词）|
| 用户提及新的时间段 | `dateRange` 更新 |
| 新建会话 | `context` 清空 |
| 用户明确说"换一只" | `tickers` 清空，等待新标的 |

---

## 4. 数据结构

```typescript
// src/stores/context.store.ts

interface ContextState {
  current: AnalysisContext
  history: AnalysisContext[]         // 最近 10 次上下文快照，用于「撤销上下文」

  updateFromToolCall: (toolName: string, params: Record<string, unknown>) => void
  updateFromMessage: (parsed: ParsedEntities) => void
  buildSystemPromptAppendix: () => string   // 拼接成 system prompt 追加文本
  reset: () => void
}
```

---

## 5. 验收标准

- [ ] 第一轮问茅台，第二轮问"它的毛利率"，工具调用参数中 ticker 为 600519.SH
- [ ] 指定时间范围后，后续问题不再追问时间
- [ ] 新建会话后，上下文完全清空
- [ ] 上下文信息在 DevToolbar 中可见（便于调试）

### 3.3 Disclaimer（合规免责声明）

**注入机制：由 LLM 自主判断，通过 `disclaimer` StreamEvent 信令驱动。禁止任何形式的关键词匹配或关键词过滤。**

实现方式：

1. **系统提示约束**：`src/services/llm/mock.ts` 和 `AnthropicLLMService` 共用的 `BASE_SYSTEM_PROMPT` 中包含如下约束：

   > 当你的回复包含以下任意内容时，你必须在流的最末尾 emit 一个 `{ type: 'disclaimer' }` StreamEvent：
   > - 使用了金融工具返回的市场数据、财务数据或行情数据
   > - 对市场走势、公司基本面、股价表现做出分析或评价
   > - 包含量化回测或风险计算的结果
   >
   > 纯代码编写、纯算法解释、与金融数据无关的通用回复，不需要 emit disclaimer。

2. **客户端处理**：`appendStreamEvent` 收到 `type === 'disclaimer'` 时，在 `streamingBlocks` 末尾追加 `{ type: 'disclaimer', content: DISCLAIMER_TEXT }` ContentBlock。

3. **免责声明文本**（固定字符串常量 `DISCLAIMER_TEXT`，不可由 AI 生成，存放在 `src/constants/disclaimer.ts`）：

   > 本分析内容仅供参考，不构成任何投资建议。数据来源可能存在延迟或误差，请以上市公司官方披露信息为准。投资有风险，入市需谨慎。

**Mock 模式**：各场景文件（`s01-roe-chart.ts` 等凡包含财务/行情数据的场景）在 events 数组末尾手动添加 `{ type: 'disclaimer' }` 事件，与真实模式行为一致。

**Mock 模式的验证局限性**：

Mock 模式下 disclaimer 是预制脚本中的硬编码事件，无法验证以下关键行为：
- LLM 是否能正确判断何时需要 emit disclaimer（误发/漏发）
- LLM 是否在纯代码回复中错误地 emit 了 disclaimer

这些行为只能在 Real 模式（阶段 0.5）中验证。阶段 0.5 的 HTCR 测试集应包含 disclaimer 正确性的专项验证：
- 10 条含金融数据的输入 → 全部应有 disclaimer
- 10 条纯代码输入 → 全部不应有 disclaimer
- 通过率要求 ≥ 90%

## 4. 验收标准

- [ ] DevToolbar 在生产构建（`npm run build`）中不渲染
- [ ] Mock → Real 切换后，旧服务实例 abort 并重建（进行中的流不会继续 yield 事件）
- [ ] API Key 不出现在 Network 请求中（客户端直连 Anthropic API）
- [ ] LLM 在包含财务/行情数据的回复末尾 emit `disclaimer` StreamEvent，客户端渲染 Disclaimer 块

- [ ] Mock 场景中所有含金融数据的场景文件（s01–s05 中的财务/行情类）包含 `{ type: 'disclaimer' }` 事件
- [ ] `DISCLAIMER_TEXT` 常量在代码库中只有一处定义（`src/constants/disclaimer.ts`），不可在 AI 回复中动态生成

# M12 · 数据源连接器框架

**优先级**：P0 · 阶段 0
**负责范围**：`registry.ts` · `MockFinanceService` · `TushareService`（stub）· `MockLLMService` · `AnthropicLLMService`（stub）

> **阶段 0 必须交付**：`registry.ts` 注册表（含 `resetServiceCache`）、所有 Mock 实现（`MockLLMService` / `MockFinanceService` / `MockExecutorService`）、所有 Real stub（接口完整、方法体抛 `NotImplementedError`）、合约测试文件骨架（Mock 实现通过）。
> **阶段 1 交付**：`TushareService` 和 `AkshareService` 真实实现（取消注释 tests 中的 Real 测试）、M05 财报数据真实接入。
> **阶段 1 交付（M04/M06 联动）**：`SandboxService` 真实实现、行情 API 真实接入、数据源健康检查与降级切换。

---

## 1. 模块目标

通过「接口 + 注册表」模式，让 Mock 实现和真实实现可以一键切换，且切换不影响任何业务逻辑代码。
所有服务的实例化逻辑集中在 `registry.ts` 一处，整个代码库其他地方只调用 `getLLMService()` 等工厂函数。

---

## 2. 功能规格

### 2.1 注册表契约（`src/services/registry.ts`）

- 每个服务提供一个工厂函数：`getLLMService()` / `getFinanceService()` / `getExecutorService()`
- 工厂函数内部读取 `config.store.useMock`，返回对应实现
- 服务实例懒加载（首次调用时实例化），并缓存
- `config.store.setUseMock()` 调用 `resetServiceCache()` 清空缓存
- `resetServiceCache()` 必须先 `abort()` 旧的 LLM 服务实例（防止切换时旧流继续 yield 事件），再清空缓存

### 2.2 各服务 Stub 规范

每个 `src/services/{type}/real.ts` 文件必须：
1. `implements` 对应接口（TypeScript 编译期检查）
2. 方法体中抛出 `NotImplementedError`（不是空函数，防止静默失败）
3. 包含一行注释说明对应的真实 SDK / API

```typescript
// src/services/finance/tushare.ts（stub 示例）
import type { IFinanceService } from './interface'

export class TushareService implements IFinanceService {
  constructor(private token: string) {}

  async getFinancialReport(): Promise<FinancialReport[]> {
    // TODO: 使用 tushare Pro API: https://tushare.pro/document/2
    throw new Error('TushareService.getFinancialReport not implemented yet')
  }

  // ... 其余方法同理
}
```

### 2.3 Mock 质量要求

所有 Mock 实现需满足：
- 响应延迟 ≥ 200ms（模拟真实网络，防止 UI 出现「太快了看不见 loading」）
- 延迟可配置（通过 `config.store.mockLatencyMs`，默认 600ms）
- 错误模拟：提供 `config.store.mockErrorRate` 参数（默认 0），设置后按概率返回错误

### 2.4 接口一致性测试

在 `tests/services/` 中，为每个接口编写「合约测试」：
同一套测试用例同时跑 Mock 实现和未来的 Real 实现，保证二者行为一致。

```typescript
// tests/services/finance.contract.test.ts
describe.each([
  ['MockFinanceService', new MockFinanceService()],
  // ['TushareService', new TushareService(TEST_TOKEN)],  // Real 就绪后取消注释
])('%s', (_, service) => {
  it('getFinancialReport 返回数组，每条含 ticker 和 period', async () => {
    const result = await service.getFinancialReport({
      tickers: ['600519.SH'], fields: ['roe'], freq: 'quarterly',
    })
    expect(Array.isArray(result)).toBe(true)
    expect(result[0]).toHaveProperty('ticker')
    expect(result[0]).toHaveProperty('period')
  })
})
```
