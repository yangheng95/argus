## Causal chain

1. **Observable:** an “unable to load this task conversation” alert appears above cards that prove the conversation is already present.
2. **Direct trigger:** right-Dock geometry is measured in CSS pixels. Windows display scaling yields a fractional `getBoundingClientRect()` width such as `437.7141723632813`. `bootstrapOverlaySettings` copied that runtime number into `overlay_settings_save`; Tauri failed command deserialization because Rust owns an unsigned-integer persisted width.
3. **Deep design cause:** the runtime view model and persisted document have different numeric domains, but the one persisted projection sanitized widths only while loading, not while constructing every outgoing settings document. Independently, `selectTask` grouped directory selection, conversation hydration, stream start, and post-hydration workspace-settings persistence under one `catch`. Every failure in that mixed responsibility was written to `taskSelectionError`.
4. **Why stopping the frontend service exposed it:** the shutdown/reselection path caused the active Task identity to be persisted after its conversation had already hydrated. The latent fractional right-Dock value failed at that later write. Because the shared `catch` classified the write as a selection failure, `Conversation.tsx` truthfully rendered the stored error before the still-present cards, but with a false “conversation load” meaning.
5. **Why the previous path did not root-fix it:** the July 19 repair intentionally made genuine partial-hydration errors visible beside partial content and retryable. Its tests covered hydrate and directory failures, but not post-hydration settings persistence. The July 13 right-Dock persistence path added a fractional runtime measurement after the original load-time pane sanitizer and did not add an outgoing-document regression.
