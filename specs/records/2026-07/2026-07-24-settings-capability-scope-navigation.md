## Design

1. Keep one tab registry, then add explicit scope-bearing tab identities rather than overloading `tool`, `skill`, and `mcp`.
2. Chat pages own a new project-level native capability assignment for the fixed `chat` Agent. Chat Tools remain the immutable code-owned pool with editable existing permissions; Chat Skills and MCP servers use explicit project assignments consumed by the same native capability resolver as `SessionLoop`. They never read `prompt_profile.active` or an Expert Squad catalog.
3. Mission Skills remain Mission-only. `Memory & Context` remains task-selected and is independent of integrations.
4. Move the real Channel page under Integrations. Do not render unimplemented GitHub, Slack, or Linear cards; future providers must arrive through a real connector registry and authenticated backend path.
5. Expert Squad Settings uses one Registry-backed exact project snapshot: installed options, selected package declaration/configuration, and its project Skill mount matrix. Package Tool/MCP declarations are read-only. It does not expose generic project MCP status and does not resolve an active runtime profile.
6. Replace the delivered `/expert-squad/capability` route instead of retaining a compatibility path. The unpublished route encoded the wrong active-runtime dependency and must not become a second source.
7. Chat capability persistence is project-owned and rejected from global and session overlays. Exact Skill references and MCP server IDs are validated before persistence. Native Chat runtime resolves only those assigned Skills and MCP servers; no prefix matching, UI-only filtering, fallback-to-all behavior, or `general` Squad alias is permitted.
8. Settings loaders use the explicit project directory. Scoped responses remain component-local and are committed only when the full request identity still matches: directory, capability owner, selected Squad ID, and refresh generation.
9. The Settings navigation presents the product term `Agent Squad` while retaining the existing internal `expert-squad` protocol. Mission Card reuses the canonical Mission Skill management surface inside the Agent Squads group; there is no duplicate Mission page. Sidebar tabs use the strong text token so the light theme renders black text and the dark theme retains accessible contrast.

## Backend Contract Supplement

The navigation delivery initially reused the active runtime catalog. That contract was deleted. The Settings scope now uses `GET /expert-squad/settings?id=<manifest-id>`, which reads the Registry-backed project inventory and returns installed options plus one exact package declaration. It never reads a task/session active identity, connects package MCP, or writes `prompt_profile.active`.

Native Chat has a separate `GET /chat/capability` inspection contract and atomic `PATCH /chat/capability` reference-mutation contract. The project-owned assignment is merged inside the project Config write lock, while the same `ChatCapability` resolver supplies native Chat Skill and exact MCP inputs to `SessionLoop`. Every project Config writer resolves and validates the final effective candidate under the file lock and exact Skill reference locks. Adding an MCP and assigning it in one patch succeeds; removing the only definition behind a Chat assignment fails before persistence, while removing a project override that reveals a valid inherited definition succeeds. Removing an assigned Skill source is rejected across the current and registered projects.

MCP runtime resolution accepts the caller-owned `Config.Info` snapshot. Cached and connecting clients carry canonical config identities; completion rechecks the current authoritative definition before publishing. OAuth writers additionally hold a revision lease and recheck credential identity. Config is committed with atomic replacement before runtime reconciliation begins, so failed persistence leaves connection/auth state untouched. Cleanup is complete-or-explicitly-failed and retryable after the definition is absent.

The Overlay keeps resource lifecycle controls in the Chat Skill/MCP pages but loads those project resources without the task/session Squad catalog. The upper Chat MCP surface is assignment-only; the lower Project MCP surface is the sole live connection status and may start configured project servers. Resource mutations invalidate the adjacent Chat assignment projection. Exact Squad selection and Chat project changes use directory/identity/request-generation checks, and a successful Chat mutation invalidates older loads, so late responses cannot overwrite the current page.
