## 一、产品北极星

### 1.1 产品愿景

让金融从业者能够用自然语言发起一个包含"数据查询 + 代码编写"的复合任务，并在同一个对话流中得到可执行的结果，无需在任何外部工具之间切换。

### 1.2 北极星指标

**混合任务闭环率（HTCR，Hybrid Task Completion Rate）**

定义：用户发出包含金融数据意图的编程请求，工具在不追问、不要求切换工具的情况下，一次性完成数据获取 + 代码生成 + 结果呈现的比率。

目标：MVP 上线后 3 个月内达到 55%，6 个月内达到 70%。

**HTCR 测量方法（可重现定义）**：

- **测试集构成**：覆盖 S01–S05 核心场景的标注指令集，每个场景各 20 条（共 100 条），由产品团队线下标注，不公开给研发团队，防止训练集泄漏。每条指令标注：场景类型、预期调用工具组合、预期输出类型（代码/图表/表格）。
- **判定规则（单条）**：满足以下全部条件方计为"闭环成功"：
  1. 工具在 ≤ 3 轮对话内完成任务，无追问；
  2. 金融工具被正确调用（工具调用日志中参数合理，ticker/日期格式正确）；
  3. 最终输出中包含预期类型的结构化内容（代码块 / 图表 / 表格，至少一项）；
  4. 输出不包含任何占位符（如 `YOUR_TICKER`、`TODO`）。
- **排除条件**：数据源超时/不可用导致的失败不计入 HTCR 分母（单独统计为「工具调用成功率」）。
- **计算公式**：$HTCR = \frac{\text{闭环成功条数}}{\text{有效测试条数}} \times 100\%$

### 1.3 辅助指标

| 指标 | 说明 | 目标（6个月）|
|---|---|---|
| 金融工具调用成功率 | 工具调用返回有效数据的比率 | ≥ 95% |
| 代码复制率 | 生成代码被用户复制/执行的比率 | ≥ 60% |
| 会话平均轮次 | 用户完成一个任务所需的对话轮次 | ≤ 3 轮 |
| 7日留存率 | 首次使用后第7天仍活跃的用户比率 | ≥ 40% |
| 意图识别准确率 | 路由层正确分类用户意图的比率 | ≥ 90% |

### 1.4 12 个月成功定义

有 3 类用户（量化研究员、基本面分析师、风控工程师）的代表性用户，均能在不阅读说明文档的情况下，用自然语言完成一个端到端的分析任务，并告诉我们"这是我日常工作中会反复用到的工具"。

## 二、用户角色

### 2.1 主要角色

**角色 A：量化研究员（Quant Researcher）**

工作特征：每天大量编写 Python，需要反复在代码编辑器和数据终端之间切换，熟悉 pandas / numpy / backtrader，对金融术语（IC、因子暴露、Sharpe）有深刻理解。

核心痛点：数据获取和代码编写分离，调试因子逻辑时缺乏领域专用错误提示。

对工具的期待：理解金融逻辑的代码建议、快速拉数据、在代码中内联解释为什么。

**角色 B：基本面分析师（Fundamental Analyst）**

工作特征：财务建模为核心工作，Python 能力参差不齐（从完全不懂到中级），每天需要快速从多个来源汇总财报数据。

核心痛点：拉数据、清洗数据、建模三件事要花大量重复时间，不熟悉代码语法。

对工具的期待：用自然语言提问就能得到数据和图表，不需要自己写代码也能用。

**角色 C：风控工程师（Risk Engineer）**

工作特征：负责 VaR、压力测试、风险归因，需要在代码层面操作风控模型，同时快速引用历史行情数据做情景分析。

核心痛点：风控代码可复用性差，历史情景数据拉取繁琐。

对工具的期待：可复用的风控代码模板，一句话触发历史情景回放。

### 2.2 次要角色

**角色 D：投研实习生**——使用门槛更低，主要受益于自然语言降低编程门槛。
**角色 E：基金经理助理**——不写代码，但需要快速获取分析结果，是输出渲染层的主要受益者。

### 2.3 非目标用户

- 纯粹的软件工程师（不涉及金融场景的通用编程）
- 个人散户投资者（合规风险 + 产品定位偏离）
- 数据科学家（非金融领域的通用 ML/AI 需求）

## 三、核心场景

核心场景是产品的"主干路径"——骨架 PRD 中定义，所有模块的设计必须支撑这些场景完整走通。每个特性 PRD 需声明自己覆盖哪些场景的哪个环节。

### S01：财报数据驱动的可视化分析

**用户角色**：基本面分析师（角色 B）

**用户输入**："帮我用过去三年茅台的季报数据算一下 ROE 的趋势，并画出来。"

**期望行为**：
1. 意图路由识别为"财务数据查询 + 代码生成 + 图表渲染"混合意图
2. 自动调用财报工具，拉取贵州茅台（600519.SH）2021–2024 季度 ROE 数据
3. 生成 Python 可视化代码（matplotlib/plotly），数据已内联在代码中
4. 渲染图表并附加一句趋势解读

**覆盖模块**：M01 M02 M05 M03 M07

**验收标准**：用户无需追问，3 轮内完成；图表可以截图直接用于报告。

---

### S02：因子代码调试与优化

**用户角色**：量化研究员（角色 A）

**用户输入**：粘贴一段动量因子代码 + "我的 IC 跑出来很低，帮我看看哪里有问题。"

**期望行为**：
1. 意图路由识别为"代码调试 + 金融逻辑审查"混合意图
2. 代码生成引擎分析代码，识别常见问题（如未做收益率对齐、存活偏差、lookback 泄漏）
3. 给出修改建议，并可选择直接输出修改后的代码
4. 如需验证，调用行情工具提供测试数据片段

**覆盖模块**：M01 M02 M03 M06 M07

**验收标准**：能识别至少 3 类量化领域的常见因子错误，建议具体到代码行。

---

### S03：数据查询封装为可复用函数

**用户角色**：量化研究员（角色 A）/ 风控工程师（角色 C）

**用户输入**："给我看一下最近 30 个交易日沪深 300 成分股的平均换手率，然后帮我把这个查询封装成一个可复用函数。"

**期望行为**：
1. 先调用行情工具拉取数据并以表格展示
2. 生成封装函数，参数化时间窗口和指数代码
3. 附带函数使用示例代码

**覆盖模块**：M01 M02 M06 M03 M07

**验收标准**：封装函数可直接在 Python 环境中运行，参数有注释。

---

### S04：历史情景压力测试

**用户角色**：风控工程师（角色 C）

**用户输入**："用 2015 年股灾期间的行情数据，跑一下我们当前组合的最大回撤。"（并附上组合持仓表）

**期望行为**：
1. 解析用户上传的持仓数据
2. 调用行情工具拉取 2015.06–2015.09 期间行情数据
3. 生成最大回撤计算代码并执行
4. 以图表展示回撤曲线，标注最大回撤日期和幅度

**覆盖模块**：M01 M02 M06 M03 M04 M07

**验收标准**：计算结果与手工计算误差 < 0.1%；图表包含清晰的时间轴和回撤标注。

---

### S05：多标的横向比较

**用户角色**：基本面分析师（角色 B）

**用户输入**："帮我比较一下宁德时代、比亚迪、亿纬锂能这三家公司最新一期的营收增速、毛利率和 PE，出一个表格。"

**期望行为**：
1. 并行调用财报工具，拉取三家公司最新财报数据
2. 计算营收增速（YoY）、毛利率、PE
3. 渲染为结构化对比表格
4. 可选：生成一句话的横向评价

**覆盖模块**：M01 M02 M05 M07

**验收标准**：三家公司数据齐全，字段定义一致（如 PE 使用 TTM），表格可直接截图使用。

## 四、能力边界（不做什么）

以下内容明确不在 MirrorCode 的能力范围内，特性 PRD 不得设计相关功能：

**不提供投资建议**：所有分析结果均为数据呈现，不出现"建议买入/卖出/持有"等表述。任何市场分析类输出必须附带免责声明（由 M11 统一注入）。

**不执行交易指令**：不接入任何交易所或经纪商 API，无委托下单功能。

**不自主修改生产代码**：所有代码修改必须由用户确认后手动执行或复制，工具不直接操作用户的代码仓库。

**不存储用户金融数据**：数据仅在会话生命周期内流转，不持久化到产品数据库。私有数据不出用户网络环境（私有化部署场景）。

**不支持非金融领域通用编程**：例如 Web 开发、机器学习通用需求、DevOps 等，不在服务范围内。

**不做实时交易监控**：不提供 tick 级别数据推送、实时 PnL 监控等需要持久连接的功能（第一阶段）。

## 五、设计原则

以下 5 条原则适用于所有模块，特性 PRD 中的设计决策若与原则冲突，需在文档中明确说明理由。

### P1：意图优先于模式切换

用户不应被迫声明"我现在要查数据"还是"我要写代码"。工具应自动识别意图，对于混合意图自动串联执行链路。

正例：用户说"帮我画一下茅台的 ROE 趋势"，工具自动完成数据拉取 + 代码生成 + 渲染。
反例：用户必须先点击"数据模式"，查完数据再切换到"代码模式"才能继续。

### P2：工具调用透明化

每次调用外部数据源时，界面必须显示数据来源（数据源名称 + 查询参数 + 数据截止时间）。用户可以点击来源查看原始数据。

正例：在财报数据旁边显示"来源：Wind，截至 2024Q3，查询时间：2025-04-01"。
反例：数据直接出现，用户不知道来自哪里、是否是最新的。

### P3：输出即可用

代码块必须能直接复制到 Python 环境运行，不应包含需要用户手动替换的占位符（如 `YOUR_TICKER_HERE`）。表格和图表的格式应可直接用于报告。

正例：代码中已内联实际的股票代码、时间窗口、数据变量。
反例：代码中有大量 `TODO` 注释要求用户自行填充。

### P4：金融错误优于代码错误

当代码逻辑有问题时，工具应优先识别金融层面的根因（如数据对齐错误、收益率计算方式有误），而不仅仅报告 Python 的语法错误或运行时异常。

正例：看到 `KeyError: 'close'`，工具分析后告知"可能是行情数据列名使用了 'Close'（大写），请检查数据源字段名"。
反例：仅输出"KeyError: 'close' at line 12"，不给任何语境分析。

### P5：最小必要上下文

工具应能从用户的自然语言中推断出尽量多的隐含参数（如"最新一期"自动对应最近的财报期，"沪深300"自动解析为指数代码 000300.SH），减少追问。当确实需要追问时，一次只问一个问题。

正例：用户说"帮我看看茅台最近的财报"，自动使用最新财报期，不追问。
反例：先问"请问您需要哪个财报期？"，再问"请提供股票代码"，多轮追问才开始执行。

## 六、质量标准（Definition of Done）

### 6.1 特性 PRD 准入标准（进入开发前的检查项）

- [ ] 声明了覆盖的核心场景编号（S01–S05 中的至少一条）
- [ ] 包含用户故事（角色 + 动作 + 价值）
- [ ] 功能边界清晰：写明哪些输入有效，哪些无效如何处理
- [ ] 错误场景覆盖：数据源不可用、用户输入缺失、执行超时
- [ ] 配套测试设计文档已存在（可同步提交）
- [ ] 与相关联模块的接口已对齐（输入/输出格式约定）
- [ ] 不违反第四章"不做什么"中的任何条目

### 6.2 开发完成标准

- [ ] 核心场景中声明覆盖的环节可以端到端走通
- [ ] 错误处理按特性 PRD 定义实现，有用户可读的错误提示
- [ ] 工具调用日志可查（来源、参数、时间戳）
- [ ] 代码生成结果可在沙箱中执行，执行成功率 ≥ 80%（基于测试用例集）
- [ ] 响应延迟：P90 ≤ 8 秒（不含大体量数据拉取的网络时间）

### 6.3 测试通过标准

- [ ] 单元测试覆盖率 ≥ 70%（核心逻辑）
- [ ] 核心场景端到端测试全部通过
- [ ] 金融数据准确性验证：随机抽取 20 条记录与权威来源比对，误差 < 0.1%
- [ ] 意图识别准确率测试：100 条标注样本，分类准确率 ≥ 90%
- [ ] 合规检查：输出中不包含任何第四章禁止的表述

## 七、词汇表

本表定义在所有特性 PRD 中统一使用的术语，禁止各文档自行定义不同含义。

| 术语 | 定义 |
|---|---|
| **会话（Session）** | 用户打开对话框到关闭的生命周期，每个会话有独立的上下文，不与其他会话共享 |
| **轮次（Turn）** | 一条用户消息 + 工具的一条完整回复，构成一个轮次 |
| **意图（Intent）** | 从用户输入中识别出的核心任务类型：代码意图 / 数据意图 / 混合意图 |
| **工具调用（Tool Call）** | 向外部数据源（如财报 API、行情 API）发起的查询请求，区别于在系统内部执行的代码 |
| **代码生成（Code Generation）** | 工具输出 Python / SQL / R 代码文本的行为，不包含执行 |
| **代码执行（Code Execution）** | 在沙箱环境中运行代码并返回结果的行为 |
| **任务（Task）** | 用户一个完整的分析需求，可能跨越多个轮次，包含多次工具调用和代码生成 |
| **混合意图（Hybrid Intent）** | 单条用户输入同时包含数据查询需求和代码编写需求 |
| **财报期（Reporting Period）** | 财务数据对应的统计周期，如 2024Q3 / 2024H1 / FY2024 |
| **标的（Instrument）** | 金融市场中可被查询和分析的对象，包括股票、指数、债券、基金等 |
| **技术指标（Technical Indicator）** | 基于价格和成交量计算的衍生数据，如 MA、MACD、RSI、ATR 等 |
| **沙箱（Sandbox）** | 隔离的代码执行环境，不能访问用户本地文件系统或互联网，仅用于运行工具生成的代码 |
| **数据源（Data Source）** | 提供金融数据的外部系统，如 Wind、tushare、akshare、企业私有数据库 |
| **渲染（Render）** | 将代码执行结果或工具返回的数据，转化为图表、表格或富文本进行展示的过程 |

## 八、模块树

模块树是骨架 PRD 的核心输出物。每个模块是一个独立的特性 PRD 槽位。优先级 P0 为 MVP 必须，P1 为第一阶段扩展，P2 为后续规划。

---

### M01 · 对话引擎

**一句话描述**：管理用户与工具之间的会话生命周期，负责消息收发、会话状态维护、历史上下文传递。

**优先级**：P0（所有其他模块的前提）

**依赖模块**：无

**对应核心场景**：S01 S02 S03 S04 S05（全部场景的入口层）

**核心能力范围**：
- 会话创建、继续、归档
- 消息格式规范（用户消息 / 工具消息 / 系统消息 / 错误消息）
- 历史上下文截断策略（当会话超过上下文窗口时）
- 工具调用状态的会话内感知（哪些工具已调用、返回了什么）

**不在本模块范围内**：意图识别（M02）、跨会话记忆持久化（M08）

---

### M02 · 意图路由

**一句话描述**：对用户输入进行意图分类（代码意图 / 数据意图 / 混合意图），并为混合意图自动规划执行链路（先数据后代码，或并行）。

**优先级**：P0

**依赖模块**：M01

**对应核心场景**：S01 S02 S03 S04 S05（全部场景的核心判断环节）

**核心能力范围**：
- 三类意图的分类识别
- 混合意图的任务分解（拆成有序子任务）
- 金融实体的基础解析（公司名 → 股票代码，"最新一期" → 财报期，"最近30个交易日" → 日期区间）
- 意图路由结果的可解释性输出（给用户一句话说明工具接下来要做什么）

**不在本模块范围内**：具体的金融领域语义理解深化（M09）

---

### M03 · 代码生成引擎

**一句话描述**：根据用户需求和/或工具调用返回的数据，生成可直接执行的 Python / SQL / R 代码。

**优先级**：P0

**依赖模块**：M01 M02

**对应核心场景**：S01 S02 S03 S04

**核心能力范围**：
- Python 代码生成（金融场景优化，优先使用 pandas / numpy / matplotlib）
- SQL 代码生成（针对结构化财务数据查询）
- 代码中内联真实数据（不使用占位符）
- 金融领域常见错误的代码层检测（收益率对齐、日期格式、缺失值处理）
- 生成代码的自动注释（关键步骤解释）

**不在本模块范围内**：代码的实际执行（M04）；代码渲染展示（M07）

---

### M04 · 代码执行沙箱

**一句话描述**：提供隔离的代码执行环境，运行 M03 生成的代码，返回执行结果（文字、数据、图表对象）。

**优先级**：P0（UI 与 Mock 沙箱）· **Real 沙箱为 P1**

### 阶段 0：MVP（验证 UI 链路完整性与交互闭环）

**目标**：S01 和 S05 完整走通，验证"财报查询 + 代码生成 + 渲染"的 UI 链路闭环。

**验收基准（Mock 模式）**：
- 5 个核心场景（S01–S05）Mock 链路全部走通，无中断、无白屏、无半渲染

**不在阶段 0 验收范围内**：
- HTCR 指标——该指标依赖真实 LLM 推理 + 真实数据源，Mock 模式下的预制脚本无法测量。HTCR 验证推迟到阶段 0.5（Real 模式接入后）。

### 10.3 MirrorCode 与 opencorvus 的关系

MirrorCode 是 **opencorvus 平台的金融分析前端模块**，不是独立产品。两者关系如下：

| 维度 | opencorvus | MirrorCode |
|---|---|---|
| 定位 | 平台级产品（CLI + Overlay + 多模块） | 金融分析对话界面（opencorvus 的一个功能面板） |
| 技术栈 | Bun + TypeScript + Tauri | React SPA（嵌入 Tauri WebView 或独立部署） |
| 代码位置 | `packages/opencorvus/` | `packages/opencorvus/ui/` 或独立 `packages/mirrorcode/`（待定） |
| 运行方式 | 可独立运行（CLI/Overlay） | 作为 opencorvus overlay 的 WebView 内容，或独立 SPA 部署 |
| 数据流 | 提供 LLM 路由、会话管理、工具编排 | 消费 opencorvus 提供的服务接口 |

**阶段 0 的集成策略**：MirrorCode 以独立 SPA 开发和验证（`npm run dev` 独立启动），通过 Mock 服务层屏蔽对 opencorvus 后端的依赖。阶段 1 将 MirrorCode 的 Real 服务层对接到 opencorvus 的实际服务（LLM 路由、金融数据连接器等），嵌入 Tauri WebView 作为 overlay 面板。

**接口对齐约束**：MirrorCode 的 `ILLMService` / `IFinanceService` / `IExecutorService` 接口定义必须与 opencorvus 的服务端接口保持一致。Mock 实现用于前端独立开发，Real 实现在集成时桥接到 opencorvus 后端。

### 10.4 独立文档（不属于 MirrorCode 特性 spec）

**`prd-stock-trading-sim.txt`**

这是一份独立的股票交易 Web 应用 PRD，定位为"在 MirrorCode 阶段 0 MVP 启动前的独立演示项目"。

- **不是 MirrorCode 的子功能或模块**，也不在任何阶段的交付列表中。
- 目的：在 MirrorCode 核心架构尚未就绪时，提供一个可独立运行、可展示给利益干系人的金融 Web 应用，用于验证前端金融终端风格和全栈技术选型（Bun + Hono + React + Tailwind + Recharts）。
- 技术栈与 MirrorCode 部分重叠（React、Tailwind），但项目结构完全独立（全栈，有 SQLite 后端和 SSE 行情模拟），不可与 MirrorCode 的 `src/` 目录合并。
- **两套 PRD 的开发互不阻塞**：`prd-stock-trading-sim.txt` 可与 MirrorCode 并行开发，完成后作为演示参考，不合并入 MirrorCode 代码库。
