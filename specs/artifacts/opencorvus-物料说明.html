OpenCorvus 任务物料包

给 OpenCorvus 的不是一句 prompt，而是一份可执行任务包。

新用户如果想让 OpenCorvus 长程、自动、可编排地完成需求，最好准备五类材料： 任务说明、任务资料、Agent Team 定义、Skills 定义、验收标准。Agent Team 和 Skills 可以先用默认配置， 但任务说明、资料和验收标准不能缺。

看完整案例 复制任务包模板
1. 任务说明 目标、范围、阶段、case。
2. 任务资料 code、doc、截图、方案、日志。
3. Agent Team 谁写代码、接 API、审代码、做测试。
4. Skills 每个 agent 需要的专用能力。
5. 验收标准 如何定义好结果和未达成。
1. 任务说明

先说明要解决什么问题，最好附一个 case

任务说明是 OpenCorvus 的入口。它不需要写成完整 PRD（Product Requirements Document，产品需求文档）， 但必须让 Requirements 和 Architect 能判断任务边界、阶段、依赖和可验收结果。

必须

目标与背景

  • 一句话目标：要做什么、为什么做。
  • 业务或技术背景：当前问题、目标用户、影响范围。
  • 非目标：明确不做什么，避免工作流扩散。
必须

阶段与依赖

  • 是否是一次性任务，还是多阶段长程工作流。
  • 阶段之间的依赖关系，例如先复刻页面，再接数据，再做测试。
  • 每个阶段是否需要单独 goal 和验收。
推荐

Case 示例

  • 输入：用户会给什么请求、点击什么页面、传什么数据。
  • 过程：系统或页面应如何响应。
  • 输出：最终用户、开发者或测试报告应看到什么。
Case

示例：TradingView Futures 长程工作流

这个 case 来自当前落盘测试用例。它适合向新用户展示一份任务说明应该长什么样：目标明确、阶段清晰、验收有落点。

任务说明示例

  1. 阶段一：页面复刻。 复刻 https://www.tradingview.com/markets/futures/， 每个组件一个 goal，图片等非代码资源复用 TradingView。
  2. 阶段二：交互和数据。 为复刻页面添加筛选、排序、详情、API（Application Programming Interface，应用程序接口）级 mock、 数据库模型和期货行情模拟引擎，展示合理实时数据。
  3. 阶段三：MirrorTest 审查。 使用 MirrorTest 专家团做功能、性能、安全和视觉测试，生成测试用例和报告，指出问题和改进建议。
2. 任务资料

把 code、doc、截图、方案等资料打成任务资料包

任务资料是 agent 判断事实的依据。资料越结构化，OpenCorvus 越能把需求拆成正确 goals，并在后续验收时追溯证据。

资料类型 应准备什么 适用任务 必要性
Code（代码） 目标仓库、关键目录、已有实现、入口文件、测试文件、禁止改动区域。 所有需要改代码的任务。 必需
Doc（文档） README、架构记录、接口文档、业务规则、历史方案、约束说明。 后端、复杂重构、跨模块任务。 必需
截图 / 设计稿 reference 截图、当前实现截图、Figma、浏览器录屏、视觉差异说明。 前端复刻、视觉 QA（Quality Assurance，质量保障）、UI（User Interface，用户界面）任务。 按任务必需
方案 / PRD 用户方案、产品需求、模块拆分、目标架构、已确认的 tradeoff。 新功能、长程项目、原创设计。 推荐
运行资料 启动命令、测试命令、环境变量、账号、fixture、seed 数据、mock 数据。 需要运行、测试、接 API、接数据库的任务。 必需
错误证据 报错日志、失败命令、trace、network、console、复现步骤。 debug、自动化修复、回归测试。 按任务必需
外部资源 第三方 API 文档、MCP（Model Context Protocol，模型上下文协议）server、OAuth、Slack/GitHub/Figma 权限。 外部系统集成、设计资源、远程协作通道。 按需
3. Agent Team 定义

可选：定义需要哪些 agent 分工

不写也可以使用 OpenCorvus 默认 agent 流程；但复杂任务最好声明期望的分工，尤其是需要写代码、接 API、审代码、做测试时。

Requirements

需求分析 agent

负责把用户描述转成可验收需求、非目标、关键约束和阻塞项。

Architect

架构 / 拆分 agent

负责拆 goals、定义文件边界、依赖顺序、风险和每个 goal 的验收方式。

Build

代码实现 agent

负责写代码、改配置、接 API、补测试、修工具链并提交可验证 diff。

Visual QA

视觉和交互审查 agent

负责真实页面截图、视觉差异、交互状态、keyboard/focus、组件可见性。

Integrity

代码和结果审查 agent

负责检查需求、diff、测试、运行证据和剩余风险是否能支撑通过。

MirrorTest

测试专家团 agent

可包含测试需求、测试架构、测试实现、测试审查、视觉测试审查等虚拟 agent。

4. Skills

可选：说明每个 agent 需要什么特定 skill

Skill 是给某个 agent 的具体方法和工具契约。默认专家团已有内置 skill；如果任务有领域知识、测试协议或工具规范，应单独提供。

Agent 可能需要的 skill 要写清楚什么 示例
Requirements 领域需求抽取、接口契约抽取、视觉需求抽取。 如何从资料中提炼 REQ、非目标、验收点。 MirrorTest 的 test-requirements skill。
Architect goal 拆分、组件映射、API 设计、测试架构。 如何拆 goal，哪些 goal 可以并行，哪些必须串行。 网页复刻按组件/region 拆 goal。
Build 编码规范、API 接入、数据库模型、测试实现、runner 使用。 代码怎么改，命令怎么跑，失败如何分类。 MirrorTest runner 必须显式提供 executable、args、run_id。
Visual QA 截图检查、reference comparison、交互状态审查。 看哪些 viewport、哪些 region、哪些交互路径。 Frontend Replica 的 source-to-render parity。
Integrity 代码审查、证据审查、风险审查、失败分类。 什么证据能通过，什么必须退回修复或标记未达成。 检查 diff、测试输出、截图、MirrorTest artifact 是否一致。
5. 验收标准

定义一个好结果，而不是只说“完成”

验收标准是 OpenCorvus 判断是否继续迭代的核心。一个好结果必须能被证据证明，不能只靠 agent 口头总结。

好结果

必须满足

  • 需求说明中的每个必须项都有实现或明确阻塞。
  • 代码 diff 与目标文件、目标 goal 对应。
  • 测试、构建、类型检查或运行命令有真实输出。
  • 视觉/UI 任务有真实页面截图和人工复核结论。
  • API / 数据任务有正反例和错误语义验证。
  • 最终报告列出未完成项、风险和后续建议。
不能算好结果

必须拒绝

  • 只有代码改动，没有运行或测试证据。
  • 只通过 lint/typecheck，却没有验证用户路径。
  • 视觉任务没有截图，或截图没有被检查。
  • 用 mock、stub、静态截图冒充真实 E2E（End-to-End，端到端）验收。
  • 缺资料时不标记阻塞，而是让 agent 猜。
  • 把失败包装成“基本完成”。

OpenCorvus 任务物料包

  1. 任务说明：目标、背景、非目标、阶段、case。
  2. 任务资料：代码路径、文档、截图、方案、日志、测试账号、启动命令、测试命令。
  3. Agent Team（可选）：需要哪些角色，例如 Requirements、Architect、Build、Visual QA、Integrity、MirrorTest。
  4. Skills（可选）：每个 agent 的专用方法、工具、协议、runner、MCP server。
  5. 验收标准：功能、视觉、API、测试、性能、安全、文档、未达成标记方式。
FAQ

给新用户的说明

这些回答用于解释为什么要准备任务包，而不是只丢一句 prompt。

Agent Team 和 Skills 是否必须写？

不是。默认专家团和基础 agent 可以工作。但复杂任务最好写清楚，尤其涉及前端复刻、API、测试、代码审查或外部协议时。

任务资料不完整怎么办？

OpenCorvus 可以先探索，但缺少关键资料时应明确标记阻塞。例如缺 source screenshot、测试账号、API 文档或启动命令时，不能把猜测结果包装成完成。

一个好 case 应该多具体？

至少说明输入、步骤、期望输出。前端任务最好包含 URL/截图/交互路径；后端任务最好包含请求、响应、错误语义和数据状态。

MirrorTest 这类外置专家团还需要什么？

需要专家团 package，包括 expert-squad.jsonc、README、selector、agent prompts、skills、tools，以及 runner 和 artifact 规则。

制作依据与边界
  • 用户要求：按 1. 任务说明；2. 任务资料；3. Agent Team；4. Skills；5. 验收标准，组织中文 HTML 成品。
  • 读取资料：README.md、specs/artifacts/长程编排测试.md、专家团 manifest / README / selector。
  • 边界：专家团是项目 package，不是全局 prompt、普通 Codex skill、UI filter 或第二套 workflow engine。
