**For each goal, define the FULL GoalContract:**
- `id`: Unique identifier (e.g., goal_bootstrap, goal_api, goal_ui)
- `title`: Short name
- `objective`: What this goal accomplishes — detailed enough for an executor who sees ONLY this goal
- `done_definition`: Concrete, verifiable pass/fail criteria. The Eval Agent uses this.
- `owned_paths`: Files this goal has EXCLUSIVE write access to (discovered from exploration)
- `depends_on`: Goal IDs this depends on (must complete first)
- `exports`: Interfaces this goal PROVIDES for dependent goals (function signatures, types)
- `imports`: Interfaces this goal CONSUMES from its dependencies
- `priority`: blocking (must pass) or advisory (nice-to-have)
- `kind`: bootstrap | feature | verification | integration | system
- `requirement_ids`: REQ-N references this goal covers (MANDATORY — empty = implicit goal)

**The objective field is critical.** Each goal executes in an isolated worktree. The executor sees ONLY:
- This goal's objective + done_definition
- This goal's owned_paths
- The shared Decision Log
- A summary of ALL sibling goals (so it knows what others are doing)

Therefore, the objective must be self-contained. Include:
- What to implement
- Key interfaces and types to use
- Expected behavior
- Edge cases to handle

## Parallel Execution & Isolation

Goals execute in parallel, each in an isolated git worktree. Maximize parallelism:

- **Parallel-first**: Default is NO dependencies. Only add depends_on for genuine data dependencies.
- **File ownership is disjoint**: Two concurrent goals MUST NOT write to the same file.
- **Shared code in bootstrap**: Types, interfaces, schemas needed by multiple goals go in a bootstrap goal.
- **Dependencies encode data flow**: If Goal B reads output from Goal A, B depends on A.
- **Anti-pattern: serial chain**: If goals form A→B→C→D→E, your decomposition failed.
