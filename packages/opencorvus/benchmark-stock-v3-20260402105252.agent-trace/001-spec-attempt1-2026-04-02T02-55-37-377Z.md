## 3. 数据库初始化与种子逻辑必须集中在 `src/db.ts`

`src/db.ts` 必须负责：

- 执行 `prd-stock-trading-sim.txt` 中给出的全部 DDL；
- 对 `users`、`sessions`、`stocks`、`price_history`、`orders`、`positions`、`daily_snapshots` 建表；
- 插入 10 只种子股票，且代码、名称、开盘价、趋势值与 PRD 表格一致；
- 服务启动时补齐每只股票最近 60 个价格点；
- 提供后端其他模块复用的数据库访问对象与必要的初始化函数。

实现约束：
- 需要保证重复启动幂等：表重复创建不报错，种子股票不重复插入，历史价格初始化避免无限膨胀或重复生成失控。
- 因为 PRD 指定 `bun:sqlite`，不得引入其他 ORM 或 query builder。
- 必须用整数 Unix 时间戳与 PRD 表结构保持一致。

## 4. 认证模块必须实现注册、登录、Bearer 鉴权与用户上下文

`src/auth.ts` 必须提供：
- `POST /api/auth/register`
- `POST /api/auth/login`
- 认证中间件，用于保护交易、持仓、历史等私有接口；
- 从 `Authorization: Bearer <token>` 解析会话；
- 将已认证用户信息写入 Hono 上下文，供 `src/trading.ts`、`src/portfolio.ts`、`src/history.ts` 读取。

行为要求：
- 注册时用户名唯一，密码使用 `Bun.password.hash()`；
- 登录时使用 `Bun.password.verify()`；
- 登录成功创建 `sessions` 记录并返回 token；
- 未认证访问私有接口返回 401；
- 返回体应包含前端所需最小信息：至少 token、用户标识、用户名、余额或初始资金提示信息；
- 认证失败时返回明确错误 JSON，不返回 HTML。

## 5. 行情模块必须提供列表、详情和 SSE 全量快照

`src/market.ts` 必须实现：
- `GET /api/market/stocks`
- `GET /api/market/stocks/:code`
- `GET /api/market/sse`

接口行为：
- `/api/market/stocks` 返回 10 只股票的列表数据，至少含代码、名称、最新价、涨跌额、涨跌幅、成交量、更新时间；
- `/api/market/stocks/:code` 返回单只股票的详情数据，至少含开盘、现价、最高、最低、成交量、趋势/涨跌信息，以及最近 60 个价格点；
- `/api/market/sse` 按 PRD 每 2 秒推送一次全量行情快照，不允许前端轮询替代；
- SSE 数据格式必须稳定，前端 `web/src/api.ts` 能直接消费；建议使用 `event: snapshot` 或默认 message 事件，但必须在前后端实现中保持一致。

约束：
- 行情公开接口原则上可匿名访问；私有数据（交易、持仓、历史）必须要求认证。
- SSE 连接需要考虑客户端断开后的订阅清理，避免内存泄漏。

## 6. 模拟引擎必须驱动价格更新与自动撮合

`src/simulator.ts` 必须实现后台行情循环，并由 `index.ts` 启动：
- 每 2 秒更新 10 只股票价格；
- 价格变化由“上一价格 + 正态随机波动 + 趋势因子”构成；
- 波动标准差按 PRD 约束为约 0.5%；
- 基于开盘价应用 ±10% 涨跌停限制；
- 更新 `stocks` 表中的 `current_price`、`high_price`、`low_price`、`volume`、`updated_at`；
- 写入 `price_history`；
- 保留最近 60 个价格点供详情页使用；
- 每轮价格更新后对 `orders` 中 `pending` 委托自动撮合：
  - 买单：市场价 `<=` 委托价则成交；
  - 卖单：市场价 `>=` 委托价则成交。

成交后的数据一致性要求：
- 买单成交：从冻结/可用资金逻辑中完成余额最终结算，更新或插入 `positions`，设置订单 `status='filled'` 和 `filled_at`；
- 卖单成交：增加用户余额，减少持仓，设置订单状态；
- 成交必须进入历史接口可见的数据来源；
- SSE 下一次快照必须反映新价格。

备注：PRD 未提供独立成交表，历史记录可基于 `orders` 中 `filled` 订单查询生成；若实现新增成交表，不应违背现有 PRD 表结构的最小要求，但优先遵从现有 DDL，避免无必要扩表。

## 7. 交易模块必须实现买入、卖出、撤单与委托列表，并正确处理冻结资源

`src/trading.ts` 必须实现：
- `POST /api/trading/buy`
- `POST /api/trading/sell`
- `POST /api/trading/cancel/:id`
- `GET /api/trading/orders`

买卖校验要求：
- 仅认证用户可访问；
- 数量必须为 100 的整数倍；
- 股票代码必须存在；
- 委托价格必须在当前价 ±10% 内；
- 买入时必须校验可用资金足够；
- 卖出时必须校验可卖数量足够。

资源冻结要求：
- 虽然 PRD 的表中没有“冻结资金/冻结持仓”字段，但又要求“撤单成功恢复资金/持仓”，因此实现必须显式维护“待成交委托已占用资源”的语义。
- 可接受的落地方式必须不偏离现有表结构，例如：
  - 买单下单时立即扣减 `users.balance` 作为冻结资金，撤单时返还，成交时不再二次扣减；
  - 卖单下单时立即扣减 `positions.quantity` 作为冻结持仓，撤单时返还，成交时不再二次扣减；
- 同时必须确保 `GET /api/portfolio` / `GET /api/portfolio/summary` 对“当前持仓”和“可卖数量”的呈现语义一致，不出现负数或重复计算。

委托列表要求：
- `GET /api/trading/orders` 至少返回订单 id、股票、方向、数量、价格、状态、创建时间、成交时间；
- 前端股票详情页需要能够只展示某股票的当前挂单，因此接口可支持 `?stock=` 过滤，但即便新增该查询参数也不能破坏 PRD 已列出的默认行为；
- 用户只能看到自己的订单。

撤单要求：
- 仅允许撤销自己的 `pending` 订单；
- 撤单成功后：
  - 买单返还冻结资金；
  - 卖单返还冻结持仓数量；
- A 用户不能撤销 B 用户订单，必须返回 403 或 404 之一，但行为需一致并在测试中固定。

## 8. 持仓与资产汇总模块必须区分持仓明细与总览

`src/portfolio.ts` 必须实现：
- `GET /api/portfolio`
- `GET /api/portfolio/summary`

`GET /api/portfolio` 应返回每个持仓条目：
- 股票代码、名称；
- 持仓数量；
- 成本价；
- 当前价；
- 市值；
- 盈亏额；
- 盈亏率；
- 如实现了冻结持仓语义，建议同时返回 `availableQuantity`，供 `web/src/pages/StockDetail*` 卖出面板提示使用。

`GET /api/portfolio/summary` 应返回：
- 总资产；
- 可用资金；
- 总市值；
- 总盈亏；
- 收益率。

计算约束：
- 总资产 = 可用资金 + 当前持仓总市值；
- 总盈亏与收益率应基于初始资金 1,000,000 和/或持仓成本一致计算，前后端口径要统一；
- 返回 JSON 结构需便于前端直接渲染，不应要求前端再做复杂聚合。

## 9. 历史模块必须提供成交历史与每日资产曲线

`src/history.ts` 必须实现：
- `GET /api/history/trades`
- `GET /api/history/daily`

`/api/history/trades` 要求：
- 仅返回当前用户相关记录；

- 以成交记录视角返回数据，即只返回已成交买卖；

`/api/history/daily` 要求：

  - 启动或交易事件期间写入快照，或
  - 若无足够历史天数，用近 30 个时间点/日期占位并平滑展示。
- 必须保证前端图表能稳定渲染，不出现空数组导致页面不可用。

注意：
- PRD 未明确快照采样时机，这是当前代码库中的一个功能空白，必须在实现中固定策略并保持可测试性。

<risks>
- `prd-stock-trading-sim.txt` 的 DDL 没有冻结字段，但测试要求“撤单成功恢复资金/持仓”；若实现口径不统一，`src/trading.ts`、`src/portfolio.ts`、`src/history.ts` 之间容易出现余额/仓位重复计算。
