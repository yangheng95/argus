title: "Data model: Task / Run / Goal / Artifact"
description: Current task-domain model for the orchestrator and engine.
---

The current engine schema lives in `packages/opencorvus/src/engine/engine.sql.ts`. Runtime readers use `packages/opencorvus/src/engine/store.ts`, which reconstructs several logical rows from append-only artifacts.

## Entity Relationships

```
EngineTask (kind: "workflow" | "build")
 ├─ EngineSpecSnapshot / EngineRequirement
 ├─ EnginePlanVersion
 │   ├─ EngineGoal[]
 │   └─ EnginePlanNode[]
 ├─ RunRow                  reconstructed from engine_artifact kind="run"
 ├─ GoalRunRow[]            reconstructed from engine_artifact kind="goal_run_attempt"
 ├─ AcceptanceRow[]         reconstructed from engine_artifact kind="acceptance"
 └─ EvaluationRow[]         reconstructed from engine_artifact kind="verification-evidence"
```

`engine_artifact` is the durable event/evidence surface for runs, goal attempts, acceptance rows, evaluations, integrity attempts, reports, diffs, images, and related records.

## EngineTask

`EngineTaskTable` stores the user request and task-level metadata:

| Field | Meaning |
|---|---|
| `kind` | `"workflow"` uses the pipeline workflow; `"build"` uses direct build |
| `executor` | `opencorvus`, `codex`, or `claude-code` |
| `request` / `title` | User-facing task contract |
| `attachments` | User-contract attachments |
| `system_artifacts` | System-generated material such as screenshots and rendered evidence |
| `criteria_results` | Rollup used by the overlay quality panel |
| `time_started` / `time_completed` / `error` | Source fields for derived task status |

There is no authoritative `engine_task.status` column. `deriveTaskStatus` projects status from task timestamps, errors, cancellation metadata, and run state.

## Requirements and Specs

`EngineSpecSnapshotTable`, `EngineSpecItemTable`, and `EngineRequirementTable` store requirements-stage outputs. The current producer is the `requirements` workflow tool / agent, not a separate public spec-writing worker stage.

## PlanVersion, Goal, and PlanNode

The Architect agent writes:

| Entity | Meaning |
|---|---|
| `EnginePlanVersionTable` | Active or superseded plan version |
| `EngineGoalTable` | Goal contract fields: objective, acceptance specs, dependencies, ownership, priority, kind |
| `EnginePlanNodeTable` | Plan graph rows that connect goals to the active plan |

`EngineGoalTable` no longer owns a status cache. UI and prompt status are derived from the goal-run attempt chain.

## RunRow

`RunRow` is reconstructed from `engine_artifact` rows with `kind="run"`. Its status is one of:

```
queued | accepted | running | blocked | completed | failed | aborted
```

`phase` still has legacy-compatible values in the type, but current workflow progress is rendered from artifacts and workflow tool side effects rather than a host phase pointer.

## GoalRunRow

`GoalRunRow` is reconstructed from `engine_artifact` rows with `kind="goal_run_attempt"`.

| Field | Meaning |
|---|---|
| `goal_id` | Goal being implemented |
| `status` | `queued / accepted / planning / running / evaluating / blocked / completed / failed / aborted` |
| `workspace_dir` / `workspace_branch` | Isolated goal workspace |
| `workspace_base_ref` / `merge_ref` | Snapshot/git references for replay and merge |
| `supersede_of` | Links retry/rework attempts without mutating prior evidence |
| `owner` | Process owner used to detect orphaned live attempts after restart |

The latest non-superseded attempt is the authoritative source for goal progress.

## Acceptance and Evaluation

`AcceptanceRow` is reconstructed from `engine_artifact.kind="acceptance"` and records candidate/publishing/delivered/failed acceptance rows. The name "delivered" here is a persisted acceptance status, not a standalone final-delivery worker or workflow step.

`EvaluationRow` is reconstructed from `engine_artifact.kind="verification-evidence"` and records task-level or goal-run evidence:

| Field | Meaning |
|---|---|
| `scope` | `goal_run` or `acceptance` |
| `status` | `pending / passed / failed / inconclusive` |
| `verdict` | `accepted / rejected / inconclusive` |
| `checks[]` | Check summaries, evidence pointers, and scorer metadata |

## Durable State

All task-domain state persists in SQLite under the configured OpenCorvus data directory. After a server restart, the UI restores task context from the engine tables and artifacts; the orchestrator continues only after a real wake/message gives it a new decision turn.
