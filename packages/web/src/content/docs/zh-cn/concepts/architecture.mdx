OpenCorvus 的职责是把自然语言请求变成已验证的代码变更。当前架构由 orchestrator 主导：每次唤醒都读取任务快照，选择显式 workflow 工具，并把证据持久化为 SQLite 行和 artifact。

如果需要可点击的当前运行架构图，见[企业级动态架构图](./enterprise-architecture.md)。

## HTTP API 运行时分层

HTTP 服务器（`packages/opencorvus/src/server/server.ts`）把路由切成两个真实层：

- **Control plane（控制面）**：`/global/*`、`/auth/*`、`/ui/*`，以及 `/log`、`/shutdown`、`/restart`，挂载在 `Instance.provide` 中间件之前。即便没有打开项目目录也能工作。
- **Project-scoped（项目作用域）**：操作当前工作区的路由（`/tasks`、`POST /task`、Task 写操作、`/session`、`/run`、`/mcp`、`/experimental`、`/panel`、`/pty` 等）跑在 `Instance.provide({ directory, init: InstanceBootstrap })` 内部。目录来自 `?directory=` 或 `x-opencorvus-directory`。
- **Task-record reads（Task 记录读取）**：`GET /task/{taskID}` 以及 Task 记录路由 `/status`、`/board`、`/progress`、`/events`、`/brief`、`/transcript`、`/runs`、`/interactions`、`/bindings`、`/operator-model-context` 和 Task conversation 读取路由都从 task 记录解析归属，不需要 `directory`。

路由 handler 不直接读 `process.env`、不直连 SQL 表、不使用 `z.any()`。`bun run api:routes-check` 保护这条边界，`bun run docs:api` 从 OpenAPI 重新生成网页 API 参考。

## Workflow 形态

内置 workflow 定义在 `packages/opencorvus/src/engine/workflow.ts`，当前只有两条：

| Workflow   | 形态                                                                                                                            | 适用场景                                          |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------- |
| `direct`   | 按需 `analyze_intent`，然后 `build`                                                                                             | 显式 `kind=build`、局部编辑、bugfix、短调试       |
| `pipeline` | 按需 `(frontend_design / frontend_research)` → `analyze_intent` → `requirements` → `architect` → per-goal `build` → `integrity` | 多文件功能、UI 复刻、重构、需要明确验收证据的任务 |

workflow 定义是给 orchestrator 的 prompt 上下文。orchestrator 可以基于证据跳过可选步骤或重新路由。`integrity` 是 pipeline 的最终 session-bound review。

## 运行时层次

```
User request
  ↓
Channel / UI / API
  ↓
Engine task row
  ↓
Orchestrator session
  ├─ typed workflow tools: requirements / architect / build / integrity / ...
  ├─ durable artifacts: runs / goal_run_attempts / verification evidence / integrity attempts / reports
  └─ explicit user interactions: questions and permissions
  ↓
Worker sessions
  ├─ requirements, architect, frontend-design, frontend-research
  ├─ 每个 goal 一个隔离 worktree 中的 build session
  └─ integrity review session
```

## 职责边界

| 组件          | 职责                                                                                     | 当前源码                                                                                         |
| ------------- | ---------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| Channel / API | 把外部输入转成 task 创建、消息和控制操作                                                 | `packages/opencorvus/src/channel/ingress.ts`、`packages/opencorvus/src/server/routes/`           |
| Engine        | 存储 task、spec、requirements、goals、plan versions、artifacts、interactions，并投影状态 | `packages/opencorvus/src/engine/engine.sql.ts`、`packages/opencorvus/src/engine/store.ts`        |
| Orchestrator  | 唯一任务级决策者；读取 `describeTask`，派发 typed tools，根据证据决定恢复路径            | `packages/opencorvus/src/orchestrator/agent.ts`、`packages/opencorvus/src/orchestrator/tools.ts` |
| Workflow      | 声明内置 `direct` / `pipeline` 建议路径，并从 artifact 投影进度                          | `packages/opencorvus/src/engine/workflow.ts`                                                     |
| Build agent   | 实现 direct task 或 architect 产出的单个 goal                                            | `packages/opencorvus/src/build/agent.ts`                                                         |
| Integrity     | pipeline 的最终系统复核；向 orchestrator 返回 pass / non-pass 证据                       | `packages/opencorvus/src/integrity/`                                                             |

## 两层循环

### 外层：Orchestrator Wake Loop

`runTaskLoop`（`packages/opencorvus/src/orchestrator/loop.ts`）按 task 串行化唤醒并调用 `Orchestrator.processTask`。每次唤醒都读取当前 describe / artifact 快照，再决定下一次 tool call。

### 内层：Session Agentic Loop

`SessionLoop`（`packages/opencorvus/src/session/loop.ts`）运行每个 worker session：

```
LLM 发出 tool call → tool 执行 → tool result 写回 → 下一轮模型调用
```

requirements、architect、build、integrity 等 worker session 都由 orchestrator 的 typed tools 创建。

## Worktree 并行

Architect 产出的 goals 存在 `engine_goal`。每次 per-goal `build` dispatch 会创建 artifact-backed goal run attempt（`engine_artifact.kind="goal_run_attempt"`），并带上独立 workspace 元数据。UI 展示的 goal 状态从最新 goal-run attempt 链派生。
